# 005 — spec 002 구현 라운드에서 배운 것

> 2026-07-25. 제약 카탈로그 개편(스펙 002) 실행 중 발견.

1. **MySQL UNIQUE는 NULL을 중복으로 안 잡는다** — `UNIQUE(column_id, def_id, purpose_code)`에서
   purpose_code가 NULL인 행은 몇 개든 들어간다. 중복 방지를 DB unique에만 맡기면 nullable 축이 있는 순간
   구멍. → nullable 컬럼이 낀 유일성은 **애플리케이션 검사 + DB unique 이중화**가 기본값.
   (통합 테스트가 잡아냄 — 우회 스위트를 API 레벨에도 두는 게 이래서 중요.)
2. **컬럼 참조 수집기는 술어 모델과 분리하니 간단해졌다** — whereConjuncts(형태 판정용)와
   columnRefs(참조 사실만)를 별도 축으로 두자, GROUP BY/HAVING/ORDER BY/함수 인자까지 하나의 visitor로
   덮였고 기존 룰은 무변경. "표현식을 이해 못 해도 식별자는 전부 수집 가능"이 핵심 — Raw로 떨어지는
   술어도 컬럼 참조는 잡힌다(과차단 우려가 소멸).
3. **위임 계약서에 DTO 전문을 넣으니 통합 수정이 0건** — 회고 002의 교훈 적용 결과. 프론트 에이전트가
   만든 client와 백엔드 DTO가 첫 컴파일에 일치했고, 에이전트의 가정(컬럼 이름 기준 id 보존, H1 무연쇄)도
   스펙에 있어서 어긋나지 않았다.
4. **스펙 검토 지시에 "구현 파일 대조"를 포함하면 스펙-코드 사이 결함이 나온다** — C1(IR이 GROUP BY를
   안 읽음)은 스펙만 봐서는 못 잡는 종류. 검토자에게 기존 코드 skim을 시킨 것이 적중.
5. 프론트 목업 세부(클래스 섹션·kind 색·칩)는 디자인 분석 문서의 한 줄 요약으로도 재현 가능했지만,
   **위임 브리프에 라벨·색·카피를 직접 박아준 것**이 재질문 없이 끝난 이유다.
