# 009 — 승인·검토 워크플로(spec 005) 구현에서 배운 것

> 2026-07-25. 거버넌스 사슬 완성(요청→승인→작성→검토).

1. **게이트를 추가하는 작업이 기존 게이트를 열 수 있다** — 가장 값진 발견. "에디터 목적 select를
   승인 요청 select로 대체"는 UI 개선처럼 보였지만, `purposeCode`가 purpose 조건부 FILTER 제약의
   **적용 여부를 결정**하는 입력이라 그대로 두면 제약이 조용히 꺼졌다(fail-open). 적대 검토가 C1로
   확인해줬고, 해법은 제거가 아니라 **승격**이었다: purposeCode를 클라이언트 입력에서 떼어내
   승인 요청에서 서버가 주입 → purpose가 "요청자가 고르는 값"에서 "승인 라인이 승인한 값"이 되며
   spec 002의 자가 면제 구멍(C9)까지 구조적으로 닫혔다.
   교훈: **새 기능이 기존 게이트의 입력을 건드리면, 그 입력의 소비처를 코드로 추적**한 뒤 설계할 것.

2. **"IR의 대상 테이블"처럼 자명해 보이는 문구가 가장 위험** — 스코프 재귀를 명시하지 않으면
   루트만 보는 구현이 자연스럽게 나오고, `WITH x AS (SELECT ... FROM users) SELECT ... FROM x` 한 줄로
   승인 범위가 뚫린다(CTE alias는 physical=false라 루트 물리 테이블이 0개가 됨). 스펙에 **집합의 정의를
   식으로** 적어야 한다("루트+전 자손 스코프의 physical 테이블 합집합, 소문자, CTE/파생 제외").

3. **HTTP 헤더는 ASCII만** — actor를 한글 이름으로 넘겼다가 `invalid header value`로 통합 테스트 8건이
   한 번에 실패. id(u1/ap1)로 바꾸니 **검증도 강해졌다**(디렉터리가 이름·역할을 해석 → 클라이언트가
   name/role을 위조할 수 없음). 제약이 설계를 개선한 사례.

4. **스텁 identity는 "한계 명문화"가 기능의 일부** — actor가 위조 가능한데 §4.2(요청자 일치)를 fail-closed
   목록에 섞어 두면 거짓 보증이 된다. 스펙 §5 머리에 "접근 통제가 아님"을 굵게 쓰고 화면에도
   "데모 — 신원 위조 가능" 배지를 상시 노출. spec 004의 "강제 안 함" 배지와 같은 계열의 처방.

5. **검토 제도의 두 구멍은 상태 리셋과 재-lint로 닫힌다** — (a) 승인된 쿼리를 수정해도 도장이 유지되면
   검토가 무의미 → 모든 PUT은 PENDING_REVIEW로 리셋. (b) 검토자가 저장 시점 lint 스냅샷을 보면
   그 사이 추가된 BLOCK 규칙을 못 본다 → 결정 직전 재-lint, 현재 BLOCK이면 승인 거부(409).

6. 위임 계약에 DTO를 다 적어도 **백엔드 DTO 자체의 누락**은 못 막는다 — directory가 `id`를 안 내려서
   프론트가 이름→id를 추측하는 코드를 만들었다. 에이전트가 이를 보고했고 백엔드를 고쳐 제거.
   **위임 보고서의 "ambiguity" 항목을 반드시 읽고 백엔드로 되먹임**할 것.
