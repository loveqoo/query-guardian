# 011 — 위생 게이트·실행 격리 구현에서 배운 것 (spec 008 M0)

## 1. "정규화 누락 한 곳"이 목록 전체를 무효화한다

`BANNED_FUNCTIONS`를 `x.methodName.uppercase()`로 비교했다. Druid는 백틱을 **함수명에 그대로 남긴다**:

```
methodName("`SLEEP`(1)") = "`SLEEP`"   →  "`SLEEP`" ∉ {"SLEEP", ...}  →  통과
```

MySQL 8.4는 `` `sleep`(5) ``를 빌트인으로 실행한다(3초 지연 실측). 즉 금지 함수 4종이 **전부** 무효였다.

이 프로젝트엔 이미 불변식이 있었다 — spec 001 §6.5 "모든 식별자는 IR에 들어가기 전에 `norm()`을 통과한다".
learning 003에서 백틱 때문에 같은 계열의 결함(테이블명·컬럼명)을 이미 고쳤는데, **새 코드가 그 불변식을
다시 어겼다**. 교훈: 식별자를 문자열로 비교하는 새 코드는 무조건 `norm()`을 통과시킨다. 리터럴 비교 지점이
불변식의 구멍이 되므로, 검토 체크리스트에 "이번 변경이 만든 식별자 비교 지점"을 축으로 넣는다.

## 2. 검사 불가를 "위반 없음"으로 보고하면 그게 fail-open이다

`checkHygiene`는 파싱 실패 시 빈 목록을 돌려줬다. lint 경로에서는 `parse`가 따로 BLOCK을 내니 무해했지만,
스펙(§5)이 위생을 **독립 단계**로 배치했으므로 그 경로에서 호출되는 순간 `INTO DUMPFILE`·`PROCEDURE ANALYSE`·
`TABLE users`(전부 Druid 파싱 거부)가 통과한다. **"못 봤다"와 "괜찮다"를 같은 값으로 표현하면 안 된다** —
`UNVERIFIABLE` 코드를 만들어 분리했다. 같은 함정이 IR의 `unverifiable` 필드였고(spec 001 §3), 두 번째다.

## 3. 같은 SQL을 두 번 파싱하면 판정 대상과 검사 대상이 갈라진다

위생용으로 2차 파싱을 붙였더니 두 개의 독립 타임아웃 레이스가 생겼다. 검토자가 타임아웃을 3ms로 좁혀
**84회 중 57회 fail-open**(위생=빈 목록, 파싱=성공)을 관측했다. 기본값 2초에서는 재현이 어렵지만
호스트 경합·GC만으로 갈라진다. `inspect(sql) → (ParseResult, hygiene)`로 합쳐 **파싱 1회**로 만들었다.
재작성(M1)도 이 경로에 얹는다 — 아니면 3차 파싱이 또 갈라진다.

## 4. 위생 규칙은 프린터 출력의 **고정점**이어야 한다

`--`를 무조건 주석으로 거부했더니, Druid가 `WHERE id > - -1`을 `WHERE id > --1`로 출력하는 케이스에서
`hygiene(sql)` 통과 → 재작성 → `hygiene(output)` 위반이 됐다. §3.0.3 "재작성 결과 자체 검증"이 이 상태로는
저장/실행 분기를 만든다. MySQL 규칙(`--` 뒤에 공백류/문장 끝)에 맞추니 오차단(`5--1`)까지 함께 사라졌다.
**교훈: 재작성이 있는 시스템의 검증 규칙은 `P(x) ⟹ P(print(parse(x)))`를 만족해야 한다.**

## 5. fail-closed는 "더 엄격한 쪽"이 아니라 "비용을 계산한 쪽"이다

AST에서 CTE 이름을 전역 수집하며 주석에 "과다 인정은 fail-closed"라고 적었다. 실제로는
`WITH user_events AS (SELECT … FROM user_events)` — 집계 CTE를 원본 테이블 이름으로 명명하는 **분석가 표준
관용구** — 를 `NO_PHYSICAL_TABLE`로 오차단했다. 오차단 비용을 계산하지 않고 "엄격하면 안전"이라고 적은 것.
정답은 이미 있었다: IR의 `AliasResolver`가 스코프 체인을 정확히 갖고 있으므로 **IR 기준으로 판정**하면 된다.

## 6. 그 오차단을 파다가 진짜 우회를 찾았다

같은 이름 CTE를 조사하면서 IR이 **CTE 본문에서도 자기 이름을 CTE로 취급**함을 발견했다. MySQL은 비재귀 CTE
본문의 자기 이름 참조를 **물리 테이블로 해석**한다:

```sql
WITH demo_users AS (SELECT id, ssn FROM demo_users) SELECT COUNT(*), MIN(ssn) FROM demo_users;
→ 실제 ssn 반환 (MySQL 8.4 실측)
```

즉 `WITH users AS (SELECT ssn FROM users) …`는 카탈로그 조회를 건너뛰어 **BLOCK 룰이 발화하지 않았다**
(spec 001 §6.2 스코프 은닉 위반). CTE 가시 범위를 "앞서 정의된 CTE만"(RECURSIVE면 자기 포함)으로 고쳤다.
**오탐 조사가 우회를 찾아내는 경로가 됐다** — 두 축은 같은 판정 로직을 반대편에서 두드리는 일이다.

## 7. 격리는 스크립트가 회귀를 잡게 만든다

`docker/apply-exec-isolation.sh`에 "**실패해야 성공**"인 검사 7종(설정 스키마·mysql.user·OUTFILE·FOR UPDATE·
임시 테이블·LOAD_FILE NULL·루틴 SECURITY_TYPE)을 넣었다. 권한은 코드 리뷰로 검증하기 나쁜 대상이고
(`GRANT SELECT, EXECUTE ON db.*`가 왜 위험한지는 정보 스키마를 조회해야 보인다), 한 줄 실행으로 재검증되는
스크립트가 문서보다 오래 산다. MySQL 함수는 `SQL SECURITY INVOKER`를 **명시**해야 한다 — 기본값 DEFINER는
생성자(root) 권한으로 도는 미래 루틴 실행 경로를 연다.

## 8. 위임 브리프에 "실측하라"를 넣으면 실측이 온다

검토 브리프에 "Druid 동작은 추론하지 말고 측정하라 — 스크래치 프로브 테스트를 만들고 끝나면 삭제하라"를
명시했더니, 검토자가 백틱 함수명·`FOR SHARE`·`FROM DUAL`·타임아웃 레이스를 **재현 명령과 함께** 보고했다.
learning 003의 "실제 jar로 확인시켜라"가 브리프 상수로 정착. 다만 검토자가 남긴 프로브 파일을 내가 지웠다 —
브리프에 "삭제"까지 적었는데도 남았으므로, 위임 후 `git status`로 잔여물을 확인하는 습관이 필요하다.

## 9. "조용히 버림"은 fail-closed가 아니다 — 스코프를 버리면 위반도 버려진다

`collectTables`의 `else` 분기에 이렇게 적혀 있었다: *"UNION table source 등 희귀 케이스: 테이블 미수집 →
귀속 불가 fail-closed"*. 절반만 맞다. 테이블을 못 세는 것은 fail-closed지만, **그 스코프 자체가 사라지는 것**은
fail-open이다:

```sql
SELECT u.id FROM users u
  JOIN (SELECT ssn AS c FROM users UNION ALL SELECT ssn AS c FROM users) d ON u.id = d.c
→ no-blocked-column 무발화 (ssn이 IR에 없다). 바깥 users 때문에 0-테이블 검사도 안 걸린다.
```

이건 §5의 "엄격하면 안전하다고 적었다"와 같은 오류의 쌍둥이다. 그때는 *과다 인정*의 오차단 비용을 안 셌고,
이번엔 *미수집*의 은닉 비용을 안 셌다. **판정 입력에서 무언가를 빼는 코드는 "무엇이 함께 빠지는가"를 적어야
한다.** 조치: UNION 테이블 소스를 자식 스코프로 등록하고, 미지원 FROM 형태는 `unverifiable`로 차단(=BLOCK).

## 10. 검증 채널마다 요청 형태가 다르다 (타사 모델)

타사 모델에 "보안 게이트의 우회를 찾아라"로 요청하니 **자체 안전 필터가 사이버 위험으로 분류해 거부**했다.
같은 코드를 "검증기와 프린터의 왕복 정합성을 확립/반박하라 + 정상 쿼리 오거부를 찾아라"로 재프레이밍하니
160개 입력을 측정해 반례 0건을 확인하고, 그 과정에서 **오탐 하나가 물고 있던 CRITICAL 우회**(위 §9)를 찾아냈다.

두 가지 교훈. ⑴ 공격 축과 정합성 축을 **다른 채널에 배분**한다 — 전자는 사내 적대 검토, 후자는 타사 모델.
⑵ 중계 계층(포워더 서브에이전트)을 거치면 상태가 사라진다(스톨·로그 소실 2회). `codex exec`로 **프로세스를
직접 소유**하고 로그 경로를 내가 정하니 종료 코드까지 남았다. 오래 걸리는 위임은 소유권을 직접 갖는다.
