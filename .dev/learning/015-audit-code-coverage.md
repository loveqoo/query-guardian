# 015 — 감사 코드 전수 검증을 설계하는 법 (spec 010 P0)

"분류 코드가 21종인데 3종만 테스트한다"를 닫는 작업에서 얻은 것. 다음에 **결말을 분류하는 어휘**
(오류 코드·상태 코드·이벤트 종류)를 만들 때 그대로 쓴다.

## 1. 어휘를 타입으로 올리는 것만으로는 안 닫힌다

`record(errorCode: AuditCode?)`로 바꾸면 *그 함수를 지나는* 값은 닫힌다. 그러나 엔티티와 리포지토리가
public이면 `save(Event(errorCode = "OOPS"))`가 그대로 통과한다. **닫힘의 범위를 정확히 적어라** —
"컴파일 시점에 닫힌다"는 대개 거짓이고, 참인 것은 "이 진입점을 지나면 닫힌다"다.

## 2. 검증의 축은 "코드별"이 아니라 **"코드 × 진입점"**

같은 코드가 여러 진입점에서 나면 한 곳만 고정한 테스트는 다른 곳의 기록 코드를 **통째로 지워도 그린**이다.
실측: 게이트 진입점이 둘(`execute`/`preview`)인데 미리보기 쪽만 고정했더니, 실행 경로의
`catch { audit.record(…); throw }` 래퍼 삭제가 검출되지 않았다. 진입점마다 시나리오를 둔다.

## 3. 단정은 **행의 계약 전체**를 덮어야 한다

`error_code`만 보면 통과하는 회귀들: `outcome`을 BLOCKED→PREVIEW로 바꾸기(감사 필터에서 사라짐),
`query_id`를 null로 만들기(쿼리별 이력에서 사라짐), 본문 미기록 자리에 SQL 넣기(권한 없는 사용자의
SQL이 감사에 복사됨), **다른 요청이 남긴 행을 보고 통과하기**(actor 미검증).
→ 새 행이 **정확히 1건**인지 + `actor`가 요청자와 같은지를 함께 단정하면 "행-요청 결속"이 생긴다.

## 4. 응답 본문의 코드도 계약이다

감사에는 남는데 응답에는 안 실리는 경로가 실측 **9개**였다. 상태 코드만 단정하면 이 어긋남이 안 보인다.
**현행이 `null`이면 `null`이라고 적어라** — 나중에 통합할 때 그 `null`들이 정확히 변경 목록이 된다.

## 5. 도달 불가 코드는 **발견**이지 결함이 아니다

전수 검증을 붙이면 "정상 입력으로 도달 못 하는 코드"가 드러난다. 실측 6/21종.
대표 사례: 판정 층이 재작성 층과 **같은 기준**을 쓰면(마스킹 표현 가능성), 판정이 먼저 BLOCK하므로
재작성의 거부 코드는 영원히 안 나온다 — 두 층이 갈라질 때만 발화하는 2선 방어다.
→ 이런 코드는 협력자를 주입해 고정하되 **그 사실을 테스트에 적는다**. 지우면 방어가 사라지고,
"실제로 발화한다"고 적으면 거짓말이 된다.

## 6. 협력자 주입의 한계를 명시하라

spy로 `ExecutionFailure(TIMEOUT)`을 던지면 "게이트가 그것을 어떤 코드로 번역하는가"는 검증되지만
**실제 JDBC 분류 경로**(`SQLTimeoutException` → `TIMEOUT`)는 한 줄도 안 돈다. 최소한 짝(enum ↔ enum)은
이름 집합 비교로 고정하고, 발화 검증은 별도 항목으로 넘긴다. 개수 비교(`size + 1`)는 한쪽에 넣고 다른
쪽에서 빼는 변경을 통과시킨다 — **이름 집합을 비교**해야 짝이 지켜진다.

## 7. 픽스처 설계 두 가지

- **"저장 이후에 세상이 바뀐다"** 를 재현하려면 저장·검토를 **먼저** 끝내고 그 뒤에 권한 회수·승인 취소·
  제약 추가를 한다. 순서가 바뀌면 게이트가 아니라 저장 게이트가 막아 시나리오에 도달하지 못한다.
  (승인 취소는 API로 안 된다 — APPROVED는 전이 불가라 DB를 직접 바꾼다. 그 상황 자체가 게이트의 방어 대상.)
- **준비 실패는 캐시해서 한 번만 진단**한다. 재시도하면 중복 등록(409·UNIQUE 위반)이 근인을 덮어
  20개의 무관한 실패에 묻힌다. 픽스처는 companion 전역 대신 `@TestInstance(PER_CLASS)` + 인스턴스
  필드에 둔다 — 전역은 Spring 컨텍스트·컨테이너 수명과 끊어진다.

## 8. 문서: 정의를 고칠 때 **사본을 먼저 grep**

게이트 순서를 §5에서 정정했는데 §2에 낡은 사본이 "확정"이라는 표시를 달고 남아 있었다. 사본은 반드시
늦게 썩고, 하필 낡은 쪽이 위험한 배치였다. **순서·목록처럼 정책인 것은 정의를 하나만 둔다.**
