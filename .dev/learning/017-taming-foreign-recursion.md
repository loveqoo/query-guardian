# 017 — 남의 라이브러리 재귀를 유계로 만드는 법 (spec 010 P1.5)

파서(Druid)의 `StackOverflowError`를 값으로 바꾸면서 얻은 것. 다음에 **내가 못 고치는 코드가 스택을
터뜨릴 때** 그대로 쓴다.

## 1. "어딘가 깊다"로 멈추지 말고 **고리를 이름으로 특정**하라

`StackOverflowError`의 스택 트레이스에서 **반복 프레임을 세면** 재귀 고리가 이름과 횟수로 나온다.

```kotlin
e.stackTrace.map { "${it.className.substringAfterLast('.')}.${it.methodName}" }
    .groupingBy { it }.eachCount().entries.sortedByDescending { it.value }
```

실측 결과 서로 **다른 고리 셋**이 나왔다(`additiveRest` 자기 재귀 / `query`↔`select`↔`parseFrom` /
`primary`↔`expr`↔`primaryLParen`). 고리마다 이음매가 다르므로 하나로 뭉뚱그리면 해법도 뭉개진다.
주의: 트레이스는 기본 1024 프레임에서 잘린다(`MaxJavaStackTraceDepth`) — **비율만 보고 절대 깊이로 읽지 말 것.**

## 2. `final`이 전부는 아니다 — 이음매를 먼저 세어라

"남의 코드라 못 고친다"는 대개 **확인하지 않은 말**이다. 실측: 셋 중 둘은 `public` 메서드라 상속으로
계수기를 끼울 수 있었다. 나머지 하나만 `final`이었고, 그건 **컴파일러에게 물어** 확정했다
(`'additiveRest' in 'SQLExprParser' is final and cannot be overridden`).

`final`이면 위쪽 이음매를 찾되, **거기서 가로채는 비용**을 재라. 우선순위 사슬 전체를 재구현해야 한다면
멈춰야 한다 — 손으로 만든 파서가 원본과 다르게 읽으면 "판정과 실행이 같은 문법을 본다"는 전제가 깨진다.

## 3. 상한은 **스택 용량이 아니라 도메인 필요치**로

상한이 스택 한계에 가까우면 **계수기가 세기 전에 스택이 먼저 터진다**(실측: 1,000은 뚫렸고 200은 잡았다).
실제 쿼리의 파싱 깊이는 **2**였다. 상한을 100으로 잡으면 계수기가 항상 먼저 도달한다.

일반화: 계수 기반 방어는 **측정된 정상치 × 여유**로 잡는다. "환경이 견디는 만큼"으로 잡으면 환경이
바뀔 때 조용히 무력해진다.

## 4. 계수기 밖 축을 찾아라 — **평면 체인**

깊이 계수기는 *파서의 재귀 깊이*를 센다. 그런데 `a OR b OR … OR z`는 파서가 **반복으로** 처리해
깊이 2로 지나가면서 **좌편향 n단 AST**를 만든다. 그 위를 걷는 모든 코드가 n단 재귀가 된다.

→ 깊이와 **연쇄 길이는 다른 축**이다. 연쇄는 텍스트 성질(리터럴 제거 후 이진 연산자 개수)로 세면
라이브러리 내부와 무관하고 버전에 안 묶인다.

## 5. 우리 재귀는 **재고 나서** 고쳐라

라이브러리 쪽에 상한을 걸면 그 아래 우리 코드의 재귀 상당수가 **자동으로 유계**가 된다(스코프 중첩이
100으로 묶이면 그 위를 걷는 재귀도 100). 다시 재니 고쳐야 할 것은 처음 목록의 **일부뿐**이었다.
계획서에 "전부 고친다"고 적었더라도, 조치 뒤 다시 재서 **이유 없는 변경은 하지 않는다.**

## 6. 방식 선택: 결과를 **합치면 트램폴린**, 담기만 하면 명시 스택

- 누산기에 담는 재귀(`flatten`류) → `ArrayDeque` 명시 스택. while 한 줄이면 된다.
- 자식 결과를 **합쳐 만드는** 재귀 → `DeepRecursiveFunction`(Kotlin stdlib). 수동 스택으로 바꾸면
  "방문"과 "결합"을 스택에 섞어야 해 코드가 망가진다.
- **꼬리재귀는 트리에 안 된다.** 호출이 둘이면 뒤엣것만 꼬리 위치다. 다만 `tailrec`을 붙여 보면
  컴파일러가 "꼬리가 아니다"를 경고로 알려 주므로 **판단의 검산 도구로** 쓸 수 있다.
- arrow 같은 라이브러리를 들이기 전에 **stdlib에 같은 것이 있는지** 보라. 트램폴린은 있다.

**순서 보존 주의**: 명시 스택은 LIFO다. 재귀판의 왼→오 순서를 지키려면 **오른쪽을 먼저 넣는다.**
순서가 바뀌면 이 저장소에서는 `scopeId` 발급 순서가 달라져 계획-재작성 짝이 깨진다.

## 7. 스레드 격리의 진짜 값은 시간이 아니라 **스택**

파싱을 별 스레드에서 돌리면 그쪽 `StackOverflowError`가 `future.get`의 `ExecutionException`으로 싸여
**값이 된다**. 시간 제한은 부수적이었다(실측상 발화하지 않음). 그러니:

- 풀 크기는 **격리용인지 병렬용인지**로 정한다. 호출자가 `get()`에서 블록하면 1:1이므로 병렬성이 아니고,
  작게 잡으면 이득 없이 정상 요청만 거부한다.
- `cancel(true)`는 인터럽트 플래그만 세운다 — **순수 CPU 작업은 멈추지 않는다.** 잔존 작업을 실제로
  막는 것은 입력을 유계로 만든 것이다.

## 8. 라이브러리 진입점을 대체할 때 **원래 계약을 바이트코드로 확인**하라

`SQLUtils.parseStatements`를 우리 파서로 갈아 끼우면서 `javap -c`로 원래 동작을 봤더니 **EOF 검사**가
있었다. 빠뜨렸으면 문장 뒤 잔여물이 조용히 버려져 멀티문 검사 우회가 됐을 것이다.
편의 함수는 대개 "생성 + 호출 + **검증**"이고, 그 검증이 보안 계약일 수 있다.
