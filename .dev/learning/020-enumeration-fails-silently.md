# 020 — 손으로 나열한 목록은 빠뜨리는 쪽으로 실패한다

**맥락**: SQL 정적 분석에서 컬럼 참조 수집이 절 여섯 개를 손으로 나열해 훑고 있었고,
목록 밖 문법 셋(`USING`·`NATURAL JOIN`·`WINDOW`)의 참조가 **표시 없이 사라졌다**. 그중 하나는
차단 컬럼의 정렬 순위를 결과 값으로 돌려주는 실제 유출이었다(spec 010 이후, retrospect 019).

정적 분석기·린터·감사 도구 어디에나 적용된다.

---

## 1. 열거의 실패는 조용하다

```kotlin
val refExprs = mutableListOf<SQLExpr>()
block.selectList.forEach { refExprs += it.expr }
block.where?.let { refExprs += it }
block.groupBy?.let { ... }
block.orderBy?.items?.forEach { refExprs += it.expr }
refExprs += allOnExprs               // ← 여기 없는 절의 참조는 IR에서 사라진다
```

빠뜨렸다는 사실이 **어디에도 기록되지 않는다.** 예외도 로그도 없고, 검사기는 "그 컬럼은 없다"고
정직하게 답한다. 그래서 테스트가 초록이고, 감사 로그도 깨끗하고, 아무도 모른다.

**대조**: 같은 파일의 다른 절반은 `expr.accept(visitor)` — 방문자가 트리를 끝까지 탄다.
그쪽은 `CONCAT`·`CASE`·스칼라 서브쿼리·개명 3단을 **형태를 몰라도** 잡았다. 20발이 전부 막힌 이유가
영리한 열거가 아니라 **열거하지 않았기 때문**이다.

## 2. 기본값을 뒤집어라 — "적은 것만 검사" → "전부 검사하고 뺄 것만 뺀다"

```kotlin
// 전(前): 검사할 것을 나열 → 새 문법마다 구멍
// 후(後): 블록 전체를 훑고, 따로 검사되는 것만 제외
collectColumnRefs(block, resolver, columnRefs)
```

제외는 **둘뿐이고 각각 이유를 적는다** — 이유 없는 제외는 다음 사람이 못 지운다.

| 제외 | 이유 |
|---|---|
| FROM의 테이블 **이름** | 컬럼이 아니다. 넣으면 테이블명이 컬럼으로 잡혀 오차단이 된다 |
| 하위 **서브쿼리** | 별도 스코프에서 판정된다. 여기서 훑으면 바깥 해석기로 귀속돼 **틀린 테이블**에 붙는다 |

이러면 새 문법이 생겨도 기본이 "수집됨"이다. 뒤집기 전에는 기본이 "빠짐"이었고,
그 차이가 곧 조용한 유출과 시끄러운 오차단의 차이다. **오차단은 눈에 띄고 누락은 안 띈다.**

## 3. 알 수 없는 것은 추측하지 말고 거부하라

`NATURAL JOIN`은 조인 키가 **문법에 없다** — 양쪽 동명 컬럼 전부가 키이고 그것은 스키마를 봐야 안다.
선택지는 셋이었다: ⑴ 카탈로그를 파서에 끌어들여 계산 ⑵ 추측해서 수집 ⑶ **거부**.

⑵는 틀리는 날 조용히 샌다(추측이 놓친 컬럼 = 검사 밖). ⑴은 파서가 카탈로그에 의존하게 되어
층이 섞인다. 그래서 ⑶ — "모른다"를 값으로 만들어 **검증 불가로 차단**한다.

이 판단의 기준: **"모른다"와 "없다"를 같은 값으로 표현하고 있지 않은가.**
둘이 같으면 모르는 것이 전부 안전으로 읽힌다.

## 4. 완전성을 물으면 **명세를 분모로** 삼아라

"우회가 더 있나?"는 사례를 모아서는 답할 수 없다. 사례의 분모가 없기 때문이다.
답이 나온 방법은 **문법을 펼쳐 놓고 코드의 목록과 하나씩 대조**한 것이다:

| 문법상 컬럼 참조 자리 | 코드 목록에 | 결과 |
|---|---|---|
| select · where · groupBy · having · orderBy · JOIN ON | 있음 | 막힘 |
| **USING · NATURAL · WINDOW** | **없음** | **뚫림** |
| LATERAL | — | 이미 거부(검증 불가) |
| FOR UPDATE · INTO OUTFILE/변수 | — | 접수 검사가 거부 |
| LIMIT · PARTITION(p) · 인덱스 힌트 | — | 컬럼 참조 아님 |

그때 비로소 "이 층에 관해서는 셋이 전부"를 **근거와 함께** 말할 수 있다.
사례를 아무리 모아도 "내가 생각한 것 안에서 0건"까지밖에 못 간다.

## 5. 같은 누락이라도 **실패 방향에 따라 심각도가 다르다**

| 룰 종류 | 표현을 놓치면 | 심각도 |
|---|---|---|
| **금지**(차단·마스킹) | 못 보고 통과 | **유출** |
| **요건**(파티션·필수 술어) | 못 찾았다고 판단 | 과차단(안전하나 못 쓰게 됨) |

그래서 금지 쪽이 먼저 정규화로 단단해졌고 요건 쪽은 열거로 남았다 — 사고가 안 났으니까.
**커버리지를 한 숫자로 세지 마라.** 누락차단 1건과 과차단 1건은 같은 값이 아니다.
누락차단은 즉시 실패, 과차단은 목록으로 고정(늘면 회귀, 고치면 목록에서 제거).

## 6. 부수 — 수집을 넓히면 검증할 것은 반대 방향이다

수집 범위를 넓히는 변경의 위험은 "여전히 뚫리나"가 아니라 **"정상 쿼리가 막히기 시작했나"** 다.
그래서 되돌려 실패(뚫림 재현) **와** 정상 쿼리 회귀(과차단 집합 불변)를 **둘 다** 확인해야 한다.
한쪽만 보면 강화하면서 제품을 못 쓰게 만든다.
