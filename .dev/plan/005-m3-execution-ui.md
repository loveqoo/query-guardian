# M3 실행 계획 — 실행 UI (spec 008 §8·§9-1, 결정 8-1)

> spec 008의 마지막 마일스톤. **백엔드 변경 0을 목표로 한다** — 실행·감사·미리보기 API는 M2와
> spec 010에서 끝났다. 필요한 백엔드 변경이 생기면 그것은 발견이므로 별도 커밋으로 가른다.

## 0. 실측 (2026-07-26)

| 항목 | 상태 |
|---|---|
| `execute`·`executions`·`preview-rewrite` API 클라이언트 함수 | **0개** — 프론트 전체 미착수 |
| 에디터 `실행` 버튼 | 존재. `message.info("실행 기능은 다음 단계에서 구현됩니다")` (정직한 스텁, spec 003 규약) |
| 에디터 탭 | `규칙 검사 결과` · `실행 결과` **이미 둘 다 있다** — 후자는 "예시" 표시된 샘플 그리드 |
| 저장된 쿼리 행 액션 | 보기 · 에디터에서 열기 · 삭제 (실행 없음) |
| 감사 화면 | 없음. 디자인에도 없음 → 신규(결정 8-1-3) |
| 캐싱 라이브러리 | **없음**(순수 `useState`) → 불변식 F1이 성립 가능 |
| Playwright | `tests/layout.spec.ts` + 스냅샷 (spec 009) — 확장 지점 |

**소비할 백엔드 API 넷**:
`POST /api/preview-rewrite` · `POST /api/queries/{id}/execute` ·
`GET /api/queries/{id}/executions` · `GET /api/executions?actor=&outcome=&before=` (+ `X-QG-Audit-Total`)

## 1. 커밋 계획

| # | 커밋 | 종료 조건 |
|---|---|---|
| C1 | API 클라이언트 + 응답 타입 4종 | 화면 변경 0. 타입이 서버 DTO와 필드 단위로 일치(수동 대조표) |
| C2 | 에디터 — `규칙 검사`에 재작성 미리보기, `실행` 상태·이유, **예시 카드 제거** | M3-1·M3-2 |
| C3 | 에디터 — 실행 결과 그리드 + 상한 3값 + 재작성 SQL 토글 | M3-3·M3-4·M3-5 |
| C4 | 저장된 쿼리 — 실행 액션 + 상세 실행 이력 탭 | M3-6 |
| C5 | 실행 감사 화면 (신규 라우트·메뉴·커서 페이징) | M3-7 |
| C6 | E2E + 화면 대조 | M3-8·M3-9 + 전 기준 재확인 |

**C2가 C3보다 먼저인 이유**: 예시 카드를 먼저 걷어내야 "실 데이터가 안 와서 빈 화면"과 "샘플이 그려져
있어서 되는 것처럼 보임"이 구분된다. 스텁이 남아 있으면 C3의 실패가 초록으로 보인다.

## 2. 각 커밋의 요점

### C1 — 클라이언트

서버 DTO(`ExecutionResultDto`·`ExecutionEventDto`·`PreviewRewriteDto`)와 필드를 **하나씩 대조**한다.
`moreRowsExist: boolean | null`을 `boolean`으로 좁히면 F2가 그 자리에서 깨진다 — 타입이 세 상태를 나른다.

`GET /api/executions`는 헤더(`X-QG-Audit-Total`)를 읽어야 하므로 기존 `rawRequest` 경로를 쓴다
(본문만 반환하는 헬퍼로는 전체 건수를 잃는다).

### C2 — 에디터: 검사와 실행을 가른다

- `규칙 검사` → lint(기존) + `preview-rewrite`. **두 호출의 실패를 따로 표시**한다: lint는 되고
  미리보기가 차단이면 그것이 정보다(저장하면 막힌다는 뜻).
- `실행` 활성 조건 = `editId != null && reviewStatus == APPROVED`. 그 외 `disabled` + Tooltip에 이유.
  세 이유를 서버 어휘로 적는다(미저장 / 검토 대기 / 반려) — 화면이 새 어휘를 만들지 않는다.
- 예시 카드(`실행 결과 예시 그리드`) 제거. 대신 "실행은 저장·검토 승인 후 가능합니다".

### C3 — 결과와 상한

푸터 규칙(결정 8-1-2):

```
평소            N rows · X.XXs · LIMIT n 적용됨
상한이 자름      N rows · X.XXs · LIMIT n 적용됨
                ⚠ 거버넌스 상한 n으로 잘렸습니다 (요청 m)
                   더 있는지: 있음 | 없음 | 확인하지 않음
```

"잘렸다"의 판정은 **서버 값으로만** 한다: `effectiveLimit == configuredCap` 이면서 사용자가 더 큰 값을
요청했을 때. 화면이 재계산하면 서버와 갈린다.

재작성 SQL은 토글이고 **기본 접힘**이다 — 열려 있으면 사용자가 원본과 혼동한다.
차단·오류는 서버의 분류 코드(`AuditCode`)를 그대로 보인다(F3·F4).

### C4 — 저장된 쿼리

- 행 액션 `실행`: 요청자 본인 + `APPROVED`에서만 활성. **STEWARD에게도 비활성**이다 —
  결정 14(대행 실행 불허)가 서버에서 막으므로 화면이 활성으로 보이면 거짓 기대를 준다.
- 상세 모달에 `실행 이력` 탭. `errorDetail`은 **서버가 준 그대로**(있으면 표시, 없으면 코드까지).

### C5 — 실행 감사 (신규)

`거버넌스` 그룹, STEWARD/ADMIN. 열: 행위자 · 결과 · 행수 · 소요 · 상한 · 코드 · 시각 · 재작성 SQL.
`outcome` 필터는 **select**(F5). 커서는 "더 보기"(마지막 행의 id를 `before`로). 전체 건수 표시.
`StewardOnly` 컴포넌트가 이미 있으므로 그것을 답습한다.

### C6 — E2E·화면 대조

`tests/execution.spec.ts` 신규. 데모 스키마·승인·검토가 선행되므로 **백엔드 픽스처 준비 경로를 먼저
확인**한다(E2E가 UI로 전 과정을 밟을지, 시드에 의존할지 — 밟는 편이 회귀를 더 잡지만 느리다).
F1은 실행 후 `localStorage`·`sessionStorage`를 전수 스캔해 결과 값의 부분 문자열이 없음을 단정한다.

## 3. 검증 (§9-1)

| 축 | 방법 |
|---|---|
| 기능 | E2E 9기준(M3-1~9) |
| 기존 약속 | spec 009 스냅샷 32검사 · 백엔드 305건 |
| 디자인 충실도 | 디자인 스크린샷과 대조(`docs/design/.../screenshots`) — 에디터·저장된 쿼리 |
| 설계 품질 | `craft-reviewer` (축 분리) |
| 보안·정합성 | `deep-reasoner` — 특히 F1·F3·F4가 실제로 성립하는지 |
| 되돌려 실패 | 새 감시자마다 + **그 감시자가 약속한 범위의 경계 밖에도** (learning 018 §8-a) |

## 4. 위험

1. **실행이 실제 DB를 건드린다.** E2E가 데모 스키마를 요구하고, 실패 시 원인이 프론트인지 백엔드인지
   흐려진다. → C6에서 백엔드 경로를 먼저 curl로 확인한 뒤 UI를 붙인다.
2. **디자인에 없는 화면(감사)의 시각 기준이 없다.** 새 관용구를 발명하면 디자인 충실도가 그 화면에서만
   깨진다. → 기존 표 화면(저장된 쿼리)의 열·태그·여백을 그대로 답습하고, 그 사실을 커밋에 적는다.
3. **픽셀 불변 스냅샷이 새 탭·버튼으로 깨질 수 있다.** 깨지면 그것은 회귀 신호이므로 스냅샷을 갱신하기
   전에 **무엇이 왜 움직였는지** 적는다(spec 009의 약속을 무르지 않는다).
4. **결과를 화면 상태에 오래 들고 있으면 F1의 정신이 흐려진다.** 라우트를 떠날 때 결과 상태를 버린다.
5. **미리보기와 실행이 다른 결과를 줄 수 있다** — 미리보기는 저장 전 SQL, 실행은 저장된 SQL이다.
   사용자가 에디터를 고친 뒤 실행하면 화면의 두 탭이 서로 다른 SQL을 말한다. → 에디터 내용이 저장본과
   다르면 실행 결과 탭에 "저장본을 실행했습니다" 표시(또는 실행 비활성). **C3에서 결정할 항목으로 남긴다.**

## 5. 하지 않는 것

백엔드 변경(발견 시 별도 커밋) · IR 트리 뷰어(백로그 1-a, 별도 스펙) · 멀티 벤더 ·
`ExecutionEventDto` 매핑 중복 제거(백로그, M3 범위 밖) · `delete` 정책 결정(사용자 대기).
