## 잘 된 것

- **적대 검토를 2번, 다른 층위에** 건 것: 스펙 단계(계약 구멍 9건)와 코드 단계(파서 표현 구멍 6건).
  둘이 잡는 결함의 종류가 완전히 달랐다 — 하나만 했으면 게이트가 백틱 하나로 뚫리는 채 출시됐다.
- **위임 병렬화**: M3 프론트(에이전트) + M1 검증(에이전트) + M2 백엔드(메인)를 동시에 진행.
  API 계약을 위임 전에 문서로 고정해 둔 것이 병렬을 가능하게 했다.
- **얇은 IR 결정**이 실전에서 검증됨: F1~F6 수정이 전부 parser/ 패키지와 IR 필드 추가로 끝났고
  룰 코드는 인스턴스 키 반영 외 거의 무변경. ArchUnit 격리가 이 경계를 지켰다.

## 어긋난 것 / 다음에 다르게

- **스펙의 "결정"이 검토로 번복될 수 있음을 처음부터 가정할 것**: purpose 자유 태그 결정(§12.1)은
  적대 검토 C9로 뒤집혔다. 결정 기록(§13)에 번복 사유를 남기는 형식이 유효했다.
- **프론트 위임 시 응답 body 형태까지 계약에 명시할 것**: 제약 추가 응답 형태를 비워 뒀더니
  에이전트가 추측했고(제약 객체 vs 테이블 전체), 통합 시 수정이 필요했다. 다음 위임 계약서에는
  모든 엔드포인트의 응답 스키마를 채운다.
- Spring Boot는 스펙의 "3.x"를 3.5.16으로 확정(4.1이 최신이지만 API 확실성 우선). PG/Trino 추가
  시점에 4.x 승격 검토.
