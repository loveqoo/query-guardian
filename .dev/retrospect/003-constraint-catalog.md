## 잘 된 것

- **검토자에게 기존 코드 대조를 시킨 것**: C1(IR이 GROUP BY/ORDER BY/함수 인자를 안 읽음 → BLOCK 룰이
  자명하게 우회됨)은 스펙 문서만으론 발견 불가한 결함이었다. "스펙 vs 구현" 대조는 검토 지시의 고정 항목으로.
- **DTO 전문을 스펙에 넣고 위임**: 프론트-백엔드 통합 수정 0건 (회고 002 교훈의 실증).
- 루프 규율 준수: 매 단계 표기, 참고 자산 줄, 검토→반영→실행→검증→회고 순서 유지.

## 어긋난 것 / 다음에 다르게

- 통합 테스트 1건 실패(MySQL UNIQUE의 NULL 처리) — DB 제약에 의존한 무결성 가정을 스펙 검토가 못 잡았다.
  **"DB 제약이 실제로 그 의미인가"는 검토 축에 추가**할 것 (learning 005-1).
- clsMismatch 경고 칩의 화면 재현은 스크린샷 검증을 생략(코드·DTO 경로만 확인) — cls 변경 시나리오
  화면 검증은 다음 라운드 카탈로그 작업 시 포함.
- 시드가 수동 curl — 재현 가능한 시드 스크립트(`docker/seed.sh` 또는 백엔드 dev 프로파일)로 만들 가치
  있음. 다음 스펙에서 스캐폴딩 후보.
