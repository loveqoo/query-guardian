# 006 — spec 005(승인·검토 워크플로) 회고

> 2026-07-25. 거버넌스 사슬 완성: 승인 요청 → 순차 승인 → 쿼리 작성 → 검토.

## 무엇을 했나

Scaffolding(다음 후보 점검) → **사용자의 모델 교정 수용**("쿼리는 승인 후 작성 — 상태는 쿼리가 아니라
요청에 있다") → 결정 3건 질문 + 스코프 확장(검토 단계) → 스펙 초안 → 적대 검토(C1~C6·H1~H8) → v2 →
M1·M2 백엔드 직접 구현 → 기존 테스트 갱신 + 승인 스위트 9건 → 시드 갱신 → M3 화면 위임 →
백엔드 DTO 결함 되먹임 → 3화면 스크린샷 검증 → 회고·커밋.

## 잘 된 것

- **사용자의 모델 교정이 설계를 바로잡았다** — 나는 "쿼리 상태 필드"를 다음 단위로 제안했는데,
  사용자가 "쿼리는 승인 후 작성하므로 상태가 없다"고 교정. 그 한마디로 스펙의 뼈대(상태는 요청과
  검토에 있음)가 정확해졌다. **도메인 모델은 사용자가 나보다 안다** — 내 전제를 먼저 말하고 검증받는 게 옳다.
- **적대 검토가 "게이트 추가가 게이트를 여는" 역설(C1)을 잡았다** — purposeCode 유실. 내가 코드
  추적으로 먼저 발견했고 검토가 독립적으로 확인. 두 경로가 만나 확신이 됐다.
- CTE 우회(C2)를 스펙 단계에서 정의로 못박고 E2E로 실증(403 + uncoveredTables).
- 백엔드 95 테스트 green, 3화면 실 연결까지 한 라운드에 완료.

## 어긋난 것 / 다음에 다르게

- **헤더 ASCII 제약을 놓쳐 통합 테스트 8건이 한 번에 빨갛게 됐다** — 한글 actor. 설계 시
  "이 값이 어디로 전송되는가(헤더/URL/바디)"를 확인했어야. 결과적으로 id 도입이 설계를 개선했지만,
  실패를 겪고 나서였다.
- **위임 보고서의 ambiguity를 즉시 되먹이는 절차가 암묵적** — directory DTO의 id 누락은 에이전트가
  보고했기에 고쳤다. 앞으로 위임 결과 수신 시 "ambiguity/deviation 항목 → 백엔드 수정 필요 여부"를
  체크 단계로 명시할 것(learning 009-6).
- spec 004에서 남긴 테스트 갭(H3/H6/C4 일부)은 이번에도 못 채웠다 — 부채로 누적 중. 다음 라운드
  시작 전에 갚을 것.
