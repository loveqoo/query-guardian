# 010 — 회고: 재작성 엔진 (spec 008 M1)

## 무엇을 했나

계획 승인 후 M1-1~M1-6을 구현했다: 스코프 식별자·불투명 AST 핸들, 방언 중립 `RewritePlan`, `exec/RewritePlanner`,
`parser/SqlRewriter`(주입 3원칙), `parser/RewriteVerifier`, `must_be_masked` 판정. 그 뒤 검증 2회(타사 모델 정합성
축 + 사내 적대 공격 축)와 **수정 2라운드**. 132 → 216 테스트.

## 검증이 잡은 것 (내가 못 잡은 것)

**타사 모델(codex)**: 왕복 정합성은 160개 입력에서 성립(반례 0). 대신 CRITICAL 1건(검증기가 항등 표현식을
통과시킴) + HIGH 3건(`LIMIT 0` 확대, DISTINCT·GROUP BY 별칭의 의미 변경).

**사내 적대 검토**: 승인된 쿼리로 **평문 PII를 반출하는 독립 경로 4개**를 MySQL 실측으로 확인. 전부 판정·계획·
검증을 통과했다(LATERAL 위장, 다중 테이블 비한정 컬럼, 상관 서브쿼리, ORDER BY 서브쿼리 오라클). 추가로
주입 극성 반전, 파생 래퍼 우회, scopeId 순번 충돌, 그리고 **내가 직전 라운드에 만든 fail-open**.

두 검토가 **겹치지 않았다** — codex는 의미 보존·정합성을, 사내 검토는 유출 경로를 찾았다. 축을 나눠 배분한 것이
맞았다(learning 011 §10). 다만 사내 검토 쪽이 압도적으로 심각한 것을 찾았다는 점에서, 보안 기능에서는
**공격 축이 우선**이다.

## 잘한 것

1. **불변식으로 뒤집은 것.** "AST의 모든 쿼리 노드가 스코프로 등록된다"를 테스트로 세우자마자 내가 모르던
   구멍(OUTER JOIN ON 서브쿼리)을 하나 더 찾았다. 열거는 새고 불변식은 남는다.
2. **검증기를 계획에서 독립시킨 것.** 도입 직후 내 부분 계획 테스트 3건을 잡았다 — 즉시 값을 증명했다.
3. **실측 습관.** codex가 환경 제약으로 REASONED-ONLY로 남긴 마스킹 충돌을 내가 MySQL로 확인해 HIGH를 확정했다.
   `setParenthesized`가 스펙과 다른 타입에 있다는 것도 직접 측정으로 잡았다.
4. **위임 브리프의 스크래치 경로 분리** — learning 011 §10의 교훈을 적용해 파일 충돌은 없었다.

## 놓친 것 / 반성

1. **함수는 공유했는데 순회 축은 공유하지 않았다.** `maskUsageOf`를 판정·재작성이 함께 쓰게 만들며
   "기준을 하나로 했다"고 커밋 메시지에 적었는데, 입력 집합(`scope.tables`)이 틀렸다. 공유의 단위를
   **함수가 아니라 "판정 전체"** 로 잡아야 했다.
2. **기존 축의 fail-closed 처리를 대조하지 않았다.** `NoBlockedColumnRule`에 있던 귀속 불가 폴백을 새 마스킹 축에
   옮기지 않아 `ssn`은 막히고 `email`만 뚫렸다. 새 판정 축 추가 시 **기존 축의 fail-closed 목록 대조**를
   체크리스트로 만들어야 한다.
3. **오차단을 고치다 보안 구멍을 냈다.** codex 지적을 급히 완화하면서 연산자·값을 보지 않는 "이미 제약됨" 판단을
   넣었다. 완화의 근거가 "다른 층이 막아줄 것"이라는 **검증되지 않은 가정**이었다. 완화는 그 가정을 테스트로
   만들 수 있을 때만 하기로.
4. **빌드 디렉터리 공유를 예상하지 못했다.** 스크래치 파일은 분리했는데 gradle `build/`가 겹쳐 결과가 섞였다.
   병렬 검증의 격리 단위는 파일이 아니라 **작업 공간**이다.
5. **"구조적으로 제거했다"를 과신했다.** 결정 13(판정된 AST를 고치므로 분기 없음)이 scopeId 순번 우연 일치에
   의존하고 있었다. 불변식 주장을 할 때는 **그것이 깨지는 경우를 테스트로 보여야** 한다.
