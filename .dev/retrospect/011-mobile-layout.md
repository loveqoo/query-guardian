# 011 — 회고: 모바일 레이아웃 대응 (spec 009)

## 무엇을 했나

사용자 요청("모바일에서 보기 어렵다")으로 spec 008 M3 앞에 끼워 진행했다. Playwright 시각 회귀 하네스를 만들고
(모바일·태블릿·데스크톱·긴 뷰포트 4종, 32검사), 셸을 서랍 내비로 전환하고, 좁은 화면 전역 규칙과 표 격리를 넣었다.
데스크톱 스냅샷은 갱신 없이 통과 = 픽셀 불변.

## 잘한 것

1. **측정을 먼저 만들었다.** "보기 어렵다"를 지표로 바꾸지 않으면 고쳤는지 알 수 없다. 결과적으로 이 하네스가
   내 수정의 부작용(2px 버튼)과 브레이크포인트 오판(태블릿 3화면)을 자동으로 잡아줬다.
2. **불변 약속에 증거를 붙였다.** 데스크톱 1280px 스냅샷이 갱신 없이 통과하는 것을 매 단계 확인했다.
   `minWidth: 460`처럼 미디어 쿼리 밖 변경이 있었는지 즉시 드러났다.
3. **원인을 브라우저에 물었다.** 1811줄 파일을 눈으로 뒤지지 않고, 넘친 요소의 조상 체인을 출력하는 프로브로
   `1fr` 함정과 높이 눌림을 특정했다. 코드 grep보다 빠르고 정확했다.

## 놓친 것 / 반성

1. **첫 지표가 증상을 재현하지 못했다.** `scrollWidth` 기준으로는 7화면이 전부 통과했다 —
   `overflow: hidden`이 잘린 내용을 감췄기 때문이다. **고치기 전에 지표를 돌려 "실패해야 할 것이 실패하는지"**
   확인해야 했다. 전부 통과하면 지표가 틀린 것이다.
2. **폭만 재고 완료라고 보고했다.** 실제 결함은 높이였고(79px 컨테이너/861px 내용), 사용자가 실기기에서
   지적해서야 알았다. 축이 하나 남아 있는지 스스로 묻지 않았다.
3. **스크린샷을 봤다고 믿었다.** `fullPage`가 내부 스크롤러의 아래쪽을 담지 못한다는 것을 몰랐다.
   3개 화면만 보고 넘어간 것도 문제였다 — 사용자가 "꼼꼼하게 보라"고 한 뒤에야 7개를 전부 봤다.
4. **전역 규칙의 부작용을 예상하지 못했다.** `min-width: 0`이 버튼을 2px로 만들었다. "넘침 제거"라는 목표에만
   맞춰 규칙을 쓰면 조작 가능성을 잃는다.

## 다음에 적용할 것

- 새 지표를 만들면 **먼저 실패시켜 본다**(고치기 전에 돌려서 알려진 결함을 잡는지 확인).
- 시각 검증은 **전 화면**을 보고, 스크롤 구조(문서 vs 컨테이너)를 먼저 파악한다.
- 전역 CSS는 "컨테이너"와 "조작 요소"를 구분한다.
- 사용자가 실기기로 보고 있을 때는 그쪽이 **1차 검증자**다 — 헤드리스 결과로 완료를 선언하지 않는다.
