# 012 — spec 008 M2(실행·감사) 회고

## 무엇을 했나

실행 인프라(격리 계정·전용 풀·읽기 전용 3중·타임아웃) + 완전 재판정 게이트 + append-only 감사 +
`execute`·`preview-rewrite` API. 디자인의 결과 표가 실제가 됐다 — `j***@naver.com`이 진짜 DB에서 나오고
평문이 응답 어디에도 없다. 백엔드 240건 통과.

## 검증을 3라운드 돌린 것이 이 작업의 전부다

| 라운드 | 채널 | 잡은 것 |
|---|---|---|
| 1 | 타사 모델(정합성 축) | **감사 계약 위반** — 미리보기 차단 2경로가 403인데 기록 0건 |
| 2 | 사내 적대 검토(공격 축) | PUT 탈취(CRITICAL), 감사 도달성, 무기록 500, `sql_mode` 치환, 승인 읽기 무제한 등 6건 |
| 3 | **2라운드 수정본**을 다시 적대 검토 | 8건 — 그중 **3건이 2라운드 수정이 만든 결함** |

3라운드가 가장 값졌다. `sql_mode`를 "치환 → 합집합"으로 바꾼 내 수정이 서버의 `ANSI_QUOTES`를 상속해,
`"ssn"`을 판정기는 리터럴로 실행기는 컬럼으로 읽는 **마스킹 우회 경로**를 열었다. 내가 "틀렸다"고 지운
옛 코드가 그 위험을 우연히 막고 있었다. 규율로 남긴다: **수정 라운드가 끝나면 수정본을 다시 공격 대상으로
올린다.** "권고를 따랐다"는 안전의 근거가 아니다.

## 반성 1 — 테스트가 통과하는 이유를 세 번 확인하지 않았다

- 과대 SQL 테스트: `dialect` 오타로 400을 받아 통과. 길이 게이트는 한 번도 안 돌았다.
- `sql_mode` 계약 테스트: 위험 모드가 **애초에 없는** 서버에서 돌아 "제거됐는가"가 자동으로 참이었다.
- 마이그레이션 테스트: "옛 모양" 픽스처를 내가 이미 새 모양으로 써서 결함을 볼 수 없었다.

셋 다 **내가 방금 만든 테스트**였고, 셋 다 "초록색"이었다. retrospect 011에서 "지표가 증상을 재현하는지
먼저 확인"을 배웠는데, 같은 실패를 형태만 바꿔 반복했다. 지금은 고친 코드를 **되돌려 실패를 확인**하는 것을
루틴에 넣었고(D1·D2 실제로 확인), 마이그레이션 픽스처는 `git show <커밋>:<경로>`에서 가져온다.

## 반성 2 — "감사가 있다"를 쓰기 경로만 보고 선언했다

기록 코드를 다 만들고 SUCCESS/BLOCKED/ERROR/PREVIEW를 다 남기게 한 뒤 "감사 완료"라고 적었다. 그런데
읽기 경로가 저장 쿼리에 매달려 있어서 ⑴ 쿼리를 지우면 404 ⑵ PREVIEW는 어떤 API로도 조회 불가였다. 게다가
읽기를 뚫고 나서도 "최근 200건" 고정이라 **새 기록으로 옛 기록을 밀어내는** 은닉이 성립했다.
**감사는 쓰기가 아니라 읽기가 완성될 때 존재한다** — 다음에 감사를 만들면 "누가, 어떤 질의로, 삭제·폭주
상황에서도 그 행에 도달하는가"를 완료 기준에 적는다.

## 반성 3 — 스키마 변경을 "새 DB에서 되는가"로만 봤다

`spring.sql.init.mode=always`를 근거로 "스키마는 매 기동 반영된다"고 믿었다. `CREATE TABLE IF NOT EXISTS`는
기존 테이블을 고치지 않는다. 컬럼 추가는 멱등 DDL로 메웠는데 **nullability는 또 빠뜨려**(D2) 검토자가 실측으로
잡았다 — 같은 함정을 같은 파일에서 두 번 밟았다. 이제 스키마를 건드리면 옛 모양 픽스처 회귀를 같이 만든다.

## 잘 된 것

- **게이트 순서를 문서로 먼저 고정**한 것: 재판정·요청자 일치·데모 매핑 총체성이 순서대로 있어 검토자가
  "무엇이 무엇보다 앞서야 하는가"로 결함을 지목할 수 있었다(D6도 이 축의 지적이다).
- **실측을 요구한 브리프**: 3라운드 검토자가 실행 중 dev DB에 롤백 프로브를 써서 D2를 "추정"이 아니라
  "ERROR 1048"로 가져왔다. 정적 추론만 요구하면 이 결함은 "가능성"으로 남았을 것이다.
- **fail-closed를 기본값으로 둔 것**: 증폭 절벽(재작성이 파서 상한을 넘음)은 내가 예상하지 못한 경로였는데
  데이터가 나가지 않았다. 예상 못 한 경로에서 안전한 쪽으로 떨어지는 구조가 실제로 값을 했다.

## 다음 작업에 넘기는 것

1. M3(실행 결과 UI)는 상한 3값(`configuredCap`·`effectiveLimit`·`moreRowsExist`)을 **그대로** 보여야 한다 —
   "LIMIT 적용됨" 한 줄로 뭉치면 백엔드에서 쪼갠 이유가 사라진다.
2. 감사 화면은 `GET /api/executions`(커서)를 쓴다. 쿼리별 이력만 쓰면 삭제·PREVIEW가 다시 안 보인다.
3. 미룬 것 5건은 spec 008 §3.8에 사유와 함께 적었다. 컬럼 수준 카탈로그 검증은 판정 축 추가이므로 별도 스펙.

[[011-mobile-layout]]에서 "사용자 실기기가 1차 검증자"를 배웠고, 이번엔 "**검토자가 실측할 수 있게 브리프를
쓰는 것**"이 같은 역할을 했다. 검증의 질은 채널 수가 아니라 **그 채널이 실제로 만져볼 수 있는가**로 결정된다.
