# 013 — 게이트 재설계 검토 3라운드 회고 (spec 010 v1→v3)

설계 문서 하나가 세 번의 검토를 거쳐 v3이 됐다. **구현을 한 줄도 쓰기 전에** 나온 회고라 남긴다 —
여기서 잡힌 것들은 코드로 갔으면 전부 되돌리기 비쌌다.

## 검토 채널

| R | 채널 | 잡은 것 |
|---|---|---|
| 1 | 사용자 직접 코드 리뷰 | R1~R6 — enum 문자열화, 객체지향 부재, 예외 6채널, 스펙이 구현 서술, 파서 타임아웃 장치, null 남용 |
| 2 | 사내 적대 검토 2건(불변식 축 / Kotlin·Spring·arrow 축, 독립) | v1의 결함 15개. **둘이 독립적으로 같은 것 3개**를 짚었다 |
| 3 | codex(타사 모델) | v2의 결함 — 그중 **스펙 자체의 모순 1건**과 내 근거의 사실 오류 2건 |

## 반성 1 — 내가 고친 것이 새 회귀였다 (v2의 PREVIEW 강등)

v1의 "감사를 러너 한 곳으로"가 403을 500으로 바꾸는 경로를 만든다는 지적을 받고, 감사를 두 연산
(`recordOrThrow`/`recordBestEffort`)으로 갈랐다. 그러면서 **PREVIEW를 best-effort로 내렸다.** 미리보기는
적용될 강제식 원문을 응답에 담는 **카탈로그 오라클**이라 현행 계약이 보안 사건으로 취급하는 자리인데,
감사 DB가 죽은 동안 그것이 무기록으로 나가게 만들었다. spec 008 M2 회고(retrospect 012)에서 배운
"수정이 새 결함을 만든다"를 **설계 문서에서 다시 반복**했다.

## 반성 2 — 불변식 두 개를 나란히 적고 모순을 못 봤다

I3 "모든 종결에 감사 1행"과 I4 "차단·오류는 best-effort"를 같은 표에 적었다. best-effort는 존재성을
보장하지 않으므로 둘은 양립하지 않는다. 구현 결함이 아니라 **스펙 자체의 모순**이었고, 두 라운드가 못 봤다.
v3는 소원을 적는 대신 사실을 적는다 — 반출이 있는 종결은 기록이 선행 조건, 없는 종결은 best-effort +
기록 실패 자체가 경보 대상.

교훈: **불변식은 "그랬으면 좋겠다"의 목록이 아니다.** 두 줄이 동시에 참일 수 있는지 확인하지 않으면
불변식표는 모순 은닉 장치가 된다.

## 반성 3 — 근거를 부풀렸다 (arrow 철회)

철회 결론은 살아남았지만 근거 4개 중 2개가 부정확했다.
- "참조 저장소의 arrow 사용은 `result {}` **한 함수뿐**" → 실제로는 부모 0~4개용 **5개 템플릿**. 좁은
  결론(전부 `Result` bind 설탕, 도메인 오류 모델 선례 아님)만 유효하다.
- "raise 단축이 `CancellationException`이라 `@Transactional`과 상호작용해 롤백이 뒤집힌다" → 과장.
  신호는 `either` 경계 안에서 값으로 복원되므로 배치를 틀렸을 때만 샌다. 그리고 **내 `stop()`이 예외
  기반이면 똑같은 문제**여서 "위험 0"은 거짓이었다.

교훈: 결론이 옳아도 근거가 부풀면 **다음 사람이 그 근거로 반대 결정을 내린다.** 근거는 결론보다 정확해야 한다.

## 반성 4 — "타입으로 막는다"고 적고 생성 경로를 안 닫았다

단계 타입의 필드만 설계하고 **누가 그 타입을 발급하는가**를 안 적었다. 생성자가 공개면 정상 단계를
거치지 않고 증거 객체를 조립할 수 있고, 인터페이스면 외부가 직접 구현한다. codex의 한 줄이 정확했다 —
**"핵심은 클래스 개수가 아니라 생성 경로 폐쇄"**. 타입 설계는 필드가 아니라 **발급 권한**이 본체다.

## 반성 5 — 수용 기준이 굿하트에 열려 있었다

- `!!` 개수 예산 → `requireNotNull`·`as`로 숫자만 준다. 실제 문제는 `parse=Success ∧ statement=null` 상관.
- 훅 목록을 테스트에 리터럴 복제 → **테스트가 "단일 정의" 불변식을 스스로 위반**한다.
- "테스트 건수 감소 0" → 빈 단정으로 바꿔도 통과.
- 감사 코드 enum 순회로 "대응 테스트 존재" 확인 → 실행 경로가 그 enum을 안 써도 통과.

전부 **측정하기 쉬운 대리 변수**를 골랐기 때문이다. spec 008 §3.8에서 "지표가 증상을 재현하는지 확인"을
배웠는데, 이번엔 지표를 *설계 단계에서* 잘못 골랐다. 대리 변수는 값이 싸서 자꾸 손이 간다.

## 잘 된 것

- **채널을 다르게 준 것.** 사내 검토 둘은 축을 갈라(불변식 / 관용구) 붙였고 겹치는 3건이 나왔다 —
  독립 채널이 같은 것을 짚으면 그건 실재한다. codex는 세 번째 관점에서 **스펙 자체의 모순**을 잡았다.
- **구현 전에 돌린 것.** 15+8건이 전부 문서 수정으로 끝났다.
- **사용자가 결정을 좁혀준 것.** "예외의 롤백 side-effect를 활용할 것이냐 피할 것이냐"라는 질문 하나가
  값 기반 선택을 자명하게 만들었고, 실측(`@Transactional`이 백엔드 전체에 감사 하나뿐)이 답을 확정했다.
