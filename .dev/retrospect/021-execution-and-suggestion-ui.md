## 1. 이 구간의 가장 큰 것 — **재는 도구가 표본을 고르고 있었다**

왕복 테스트(`FixRoundTripTest`)를 만들 때 완료 기준을 이렇게 썼다:

```kotlin
assertTrue(!after.blocked, "제안대로 고쳤는데 여전히 막힌다")
```

"제안을 적용하면 **위반이 없어진다**" — 자연스러워 보인다. 그런데 이 한 줄이
**위반이 둘 이상 나오는 쿼리를 전부 배제**한다. 셀프 조인·UNION·제약 둘인 테이블은 조각 하나로
`blocked`를 끌 수 없으므로, 시나리오로 추가하는 순간 빨간불이 되고 **그래서 아무도 추가하지 않는다.**

나는 그 사실을 모른 채 커버리지를 주장했다 — 시나리오 5개 + `Fix::class.sealedSubclasses` 전수 대조.
전수는 맞다. 단 **종류의 전수이고 형태의 전수가 아니다.**

### `retrospect 019`와 무엇이 다른가

019에서 "표본으로 안전을 보지 마라, **분모를 밝혀라**"를 배웠고 이번엔 밝혔다.
그런데 밝힌 분모가 **도구에 의해 이미 좁혀져 있었다.** 나는 "무엇을 셌는가"는 물었지만
**"내 자가 무엇을 못 세게 만드는가"**는 안 물었다.

| | 019에서 배운 것 | 이번에 나온 것 |
|---|---|---|
| 질문 | 분모가 무엇인가 | **분모를 정하는 것이 무엇인가** |
| 실패 모양 | 표본을 전수로 말함 | 표본이 도구에 의해 걸러짐 — **정직하게 세도 틀림** |
| 발견 경로 | 사용자가 밀어서 | **타자 검증이 지적해서** (내가 5번을 더 봐도 못 봤을 것) |

기준을 "**그 조각이 겨눈 위반**이 사라졌는가"로 바꾸자 어려운 형태가 들어올 수 있게 됐고,
넣자마자 전부 빨간불이 켜졌다. 반례 넷이 그 자리에서 재현됐다.

**처방**: 완료 기준을 쓸 때 **"이 기준이 어떤 사례를 추가 불가능하게 만드는가"**를 한 번 묻는다.
답이 "어려운 사례"면 기준이 틀린 것이다 — 어려운 것을 재려고 만든 도구이므로.

## 2. 검증이 잡은 것 여섯 — **내가 왜 못 봤는지**까지

축을 갈라 두 채널을 돌렸고 둘 다 진짜를 찾았다. 요약하지 않고 하나씩 적는다.

| # | 발견 | 내가 못 본 이유 |
|---|---|---|
| ⑴ | 두 적용기가 **이미 갈라져 있었다**(리터럴 공백 vs `\s`) | "같은 규칙이어야 한다"를 **양쪽 주석에 적고** 장치를 안 만들었다. 시나리오가 전부 한 줄이라 테스트도 못 봤다 |
| ⑵ | 첫 `WHERE`를 고쳐 **CTE 안으로** 들어감 | 적용기를 만들며 "조각을 어디에 넣을지는 문법이 이미 정해 준다"고 썼다. 문법은 정해 주지 않는다 — **내가 상상한 SQL 안에서만** 정해 줬다 |
| ⑶ | UNION 두 팔 — 두 번째 팔 도달 불가 | 같은 뿌리(§1). 이 형태를 테스트에 넣을 수 없었으니 생각도 안 났다 |
| ⑷ | 문자열 리터럴 `'email'`을 치환 | 경계 조건을 셋이나 적어 두고(앞 식별자·점·괄호) **리터럴은 축이 다르다**는 것을 못 봤다 |
| ⑸ | 에디터가 **소유자 검사를 통째로 빠뜨림** | C2에서 만들고 C4에서 `runnable.ts`를 만들며 "합쳐야 하나"를 안 물었다. **같은 세션 안에서 두 번째 사본** |
| ⑹ | 사용자 규칙 채널이 purpose 밖에서도 값을 말함 | "새 노출이 아니다"를 시스템 룰 채널만 보고 단정했다 — 채널이 둘인 것을 알면서 |

⑸는 특히 아프다. 커밋 메시지에 *"활성으로 보이면 거짓 기대를 준다"*고 쓰고, 그 문장을 쓴 화면 옆에서
정확히 그 증상을 남겼다. `retrospect 015`가 이미 같은 축을 남겼다(**"사본은 세지 말고 자유변수를 세라"**).
백엔드에서 고친 것을 프론트에 새로 만들었다 — **처방이 층을 안 건넜다.**

### 두 채널이 겹친 것

`applyFix` 갈라짐은 **양쪽이 각각** 잡았다(보안 채널은 "화면이 다루는 입력 형태를 왕복이 안 밟는다"로,
설계 채널은 "동기화를 주석에 맡겼다"로). 축이 다른데 같은 곳을 짚으면 그것은 실재다 —
`retrospect 015`의 관찰이 다시 확인됐다.

## 3. 감시자가 신호를 삼키고 있었다

C6에서 데스크톱 픽셀 불변을 재려다 발견: 내비게이션 항목 하나를 추가하자 사이드바가 **모든 화면에서**
밀렸는데 7개 중 1개만 실패했다. 허용 오차 `maxDiffPixelRatio: 0.01`이 1280×900에서 **약 11,500픽셀**이다.

그 값의 근거는 주석에 있었다 — *"폰트 앤티에일리어싱 차이로 실패하면 신호가 죽는다."*
그럴듯하지만 **재 본 적 없는 방어막**이었고, 실제로 죽인 것은 신호였다.
재 보니 잡음 바닥은 0이었다(4회 연속 40/40). 0으로 바꾸니 76픽셀 변경도 잡힌다.

**발견 경로가 우연이었다는 것이 더 중요하다.** admin 하나만 실패한 것이 설명이 안 돼서 팠다.
admin도 1% 아래였으면 전부 조용히 통과했고 나는 "픽셀 불변 확인"이라고 적었을 것이다.

`memory: verify-your-own-guards`("감시자와 제약도 측정 대상")의 **물려받은 감시자** 판이다.
내가 만든 것만 재고 있었다.

## 4. 잘된 것

**⑴ 착수 직전 실측이 fail-open을 막았다.** M3(화면)에 들어가기 전에 서버가 *실제로* 하는 일을
확인했더니 조건 끼워넣기가 살아 있었고, **그냥 지우면 새는 자리**(INTEGRITY를 아무도 요구하지 않음)가
있었다. 순서를 S1(덮는다) → S2(지운다)로 잡은 것이 이 구간에서 가장 값진 판단이다.
반대로 했으면 그 구간이 통째로 fail-open이었고, 데모에 INTEGRITY 제약이 없어 **티도 안 났을 것이다.**

**⑵ 빨간불을 먼저 봤다** — S1(형태 둘이 실패), 검증 반영(어려운 형태 넷이 실패). 고치기 전에
실패시켜 본 것이 "이 테스트가 정말 그것을 재는가"를 매번 확인해 줬다.

**⑶ 되돌려 실패를 감시자마다, 그리고 그물의 순서까지.** 시나리오 없는 `Fix` 종류를 추가하자
**그물 셋이 순서대로** 걸렸다 — DTO 매핑 `when` → 적용기 `when` → `sealedSubclasses` 전수 대조.
하나만 확인하고 넘어갔으면 앞의 둘이 있는 줄 몰랐을 것이다.

**⑷ 회고 020의 처방을 바로 적용했다.** spec 013 §2 결정표가 전부 **사용자 원문 인용**을 달고 있다.
인용할 문장이 없는 것은 하나도 안 적었다. 처방이 다음 턴에 실제로 작동한 첫 사례다.

**⑸ 회수한 것을 세었다.** S2가 오차단 하나를 없앴다(LEFT JOIN 실행 거절). 삭제 작업에서
**무엇이 좋아졌는지**를 테스트로 고정한 것은 처음이다 — 보통은 "안 깨졌다"만 확인한다.

**⑹ 못 덮은 것을 적었다.** 감사 화면의 픽셀 비교 불가, 조각의 스코프 부재, purpose 유출의
**고치는 방향까지**(잘못 잡으면 판정이 좁아져 fail-open) 백로그에 남겼다.
