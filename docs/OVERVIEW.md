# Query Guardian — 프로젝트 개요

**통제된 환경에서 안전하게 SQL을 작성·승인·실행하는 거버넌스 서비스.**

사용자가 에디터에 SQL을 쓰면 문자열이 아니라 **구조로 분해해서** 등록된 거버넌스 규칙으로 판정한다.
위반이면 저장·실행을 막고 **어디를 어떻게 고쳐야 하는지 조각으로 알려 준다.**
통과하면 승인 절차를 거쳐 저장되고, 격리된 계정으로 실행되며, 실행의 결말은 감사에 남는다.

> **현재 상태**: 단일 개발자 프로젝트, MySQL 단일 방언, 데모 데이터 기준.
> 운영 배포를 전제한 물건이 아니며, **못 하는 것은 4부에 전부 적었다.**

> **이 문서의 층 안내**
> - [**1부**](#1부--무엇을-푸는가) 무엇을 푸는지와 어떻게 쓰는지 — 배경 지식 없이 읽을 수 있다.
> - [**2부**](#2부--거버넌스-모델) 거버넌스 모델 — 정책·보안·컴플라이언스 담당이 볼 자리.
> - [**3부**](#3부--아키텍처-리뷰) 아키텍처 리뷰 — 코드와 설계 결정.
> - [**4부**](#4부--정직한-한계) 지금 못 하는 것 — 이 문서에서 가장 먼저 읽어도 좋다.
> - [**5부**](#5부--이-저장소가-일하는-방식) 이 저장소가 일하는 방식.
>
> 바로 돌려 보려면 → [실행](#실행)

# 1부 — 무엇을 푸는가

## 1.1 문제: "권한을 줬는데 무엇을 볼지는 모른다"

데이터 접근 통제는 보통 **테이블·컬럼 단위 권한**에서 멈춘다. 그런데 실무의 요구는 그 축이 아니다.

- "고객 이메일은 **가려서** 봐야 한다" — 컬럼 권한은 보이거나 안 보이거나 둘뿐이다.
- "마케팅 목적이면 **동의한 사용자만**" — 행 단위 조건이고, 목적에 따라 달라진다.
- "이벤트 테이블은 **날짜 조건 없이** 조회하면 안 된다" — 조건이 없으면 DB가 수년치를 통째로 훑어
  운영 사고가 난다.
- "삭제 표시된 행은 **언제나** 제외" — 목적과 무관하게 항상.

그래서 현실에서는 이 요건들이 **사람의 검토**로 처리된다. 쿼리를 슬랙에 붙이고, 누군가 눈으로 보고,
"이건 괜찮네" 하고 넘긴다. 문제는 세 가지다.

1. **일관되지 않는다.** 같은 쿼리를 다른 사람이 보면 다른 답이 나온다.
2. **근거가 남지 않는다.** 왜 통과됐는지가 대화 기록에만 있다.
3. **우회가 조용하다.** `WHERE consent_yn = 'Y' OR 1 = 1`은 눈으로 보면 보이지만,
   `WITH` 절(CTE) 안에 넣고 서브쿼리로 감싸면 안 보인다.

Query Guardian은 **이 검토를 기계가 하게 만든다.** 그리고 기계가 판정할 수 없는 것은
사람에게 넘기지 않고 **막는다**.

## 1.2 기존 방식과 무엇이 다른가

| | 하는 일 | 한계 |
|---|---|---|
| **DB 권한 (GRANT)** | 테이블·컬럼 접근 허용/거부 | 행 조건·마스킹·목적을 표현할 수 없다 |
| **뷰 / 행 수준 보안** | 미리 만든 안전한 뷰만 노출 | 뷰를 만들 때마다 사람이 필요하고, 조합이 폭발한다 |
| **SQL 프록시 / 방화벽** | 패턴 매칭으로 위험한 쿼리 차단 | 문자열 매칭이라 공백·주석·대소문자로 뚫린다 |
| **쿼리 재작성 게이트웨이** | 서버가 SQL에 조건·마스킹을 자동 주입 | 주입이 의미를 뒤집을 수 있다 (바로 아래) |
| **Query Guardian** | SQL을 구조로 이해하고 규칙으로 판정, 위반이면 **막고 제안** | 판정할 수 없는 문법을 쓰면 정당한 쿼리도 막힌다(**과차단**) |

핵심 차이는 두 가지다.

**⑴ 문자열이 아니라 구조를 본다.** 파서를 통과시켜 구조로 바꾼 뒤 판정한다.
주석 삽입·공백·대소문자·백틱으로 흔들리지 않는다.

**⑵ 서버가 사용자의 SQL을 고치지 않는다.** 막고, 고칠 조각을 주고, 사용자가 고친다.
자동 주입 방식을 만들었다가 버렸는데, 이유는 실측 하나였다.

> "동의한 사용자만" 조건을 서버가 `NOT EXISTS` 안에 끼워 넣었더니
> 결과가 정확히 **비동의자만** 남았다. 보호하려던 사람들을 골라내는 도구가 됐다.

부정 문맥에서 조건 주입은 필터를 **반전**시킨다. 자세한 것은 [2.4](#24-판정하고-제안한다--서버는-사용자-sql을-바꾸지-않는다).

## 1.3 한 장면 — 막히고, 조각을 받고, 통과한다

데모 데이터는 세 테이블이다.

```
users               id, email, name, phone, ssn, created_at
marketing_consents  id, user_id, consent_yn, consent_at
user_events         id, event_date
```

거버넌스 담당(STEWARD)이 카탈로그에 이렇게 등록해 뒀다고 하자.
규칙이 요구하는 형태를 이 문서에서는 **강제식**이라고 부른다.

- `users.email` → **마스킹 필요**, 강제식은 `mask_email({col})`
- `users.ssn` → **참조 금지**
- `marketing_consents.consent_yn` → 목적이 `marketing`일 때 **`= 'Y'` 필수**
- `user_events.event_date` → **파티션 키**(경계 조건 필수)

분석가는 먼저 **승인된 요청서를 고른다.** 요청서에는 대상 테이블과 **목적**이 적혀 있고,
목적은 여기서만 나온다 — 클라이언트가 고를 수 없다(2.3). 목적이 `marketing`인 요청서를 고르고 쓴다.

```sql
SELECT u.email, u.name
FROM users u
JOIN marketing_consents mc ON u.id = mc.user_id
```

**막힌다.** 차단 사유 둘이 각각 조각과 함께 나온다.

```
✗ must-be-masked    users.email은 가려서 조회해야 합니다
                    [적용]  email  →  mask_email(email)
✗ require-predicate  marketing_consents에 필수 조건이 없습니다
                    [적용]  + mc.consent_yn = 'Y'
⚠ require-limit      행 상한이 없습니다
```

`[적용]`을 누르면 **에디터의 텍스트가 바뀌고 즉시 다시 판정된다.** 서버를 부르지 않는다.

```sql
SELECT mask_email(u.email), u.name
FROM users u
JOIN marketing_consents mc ON u.id = mc.user_id
WHERE mc.consent_yn = 'Y'
```

통과. 이제 저장할 수 있다. 그런데 **저장했다고 실행되지는 않는다** —
저장된 쿼리는 `검토 대기` 상태로 들어가고, 거버넌스 담당의 **쿼리 검토 승인**을 받아야 실행 가능해진다.
즉 관문이 둘이다: 요청서 승인(무엇을 볼 자격이 있는가) → 쿼리 검토(이 SQL이 그 자격 안에 있는가).

실행되면 결과는 화면에만 나오고 **어디에도 저장되지 않는다.**
실행 사실·행 수·소요 시간·상한 정보는 감사에 남는다.

## 1.4 기대되는 활용

**⑴ 데이터 요청 창구의 대체.** 지금 "이 데이터 좀 뽑아 주세요 → 담당자가 직접 쿼리"로 도는 흐름을,
요청자가 직접 쓰되 규칙이 지키게 만든다. 담당자는 **쿼리를 대신 쓰는 대신 규칙을 등록**한다.

**⑵ 감사 대응 자산.** "누가 언제 조회했는가"에 더해 **원문 SQL과 실행 결말**이 함께 남는다 —
어떤 마스킹 함수를 써서 조회했는지가 원문에 그대로 있으므로 사후 대조가 된다.
(다만 서버가 적용한 강제식 목록이 따로 남지는 않는다 — 4.1 참조.)

**⑶ 규칙의 실험대.** 규칙을 등록하고 기존 쿼리들을 다시 판정해 보면
"이 규칙을 켜면 무엇이 막히는가"를 켜기 전에 알 수 있다.

**⑷ 온보딩·교육.** 신규 입사자가 규칙을 몰라도 된다. 틀리면 화면이 알려 주고 고칠 조각을 준다.
문서를 읽게 하는 것보다 강하다 — 문서는 안 읽지만 빨간불은 봐야 한다.

**⑸ AI 에이전트의 안전한 손.** 사람이 아니라 에이전트가 SQL을 쓰는 시대에,
이 게이트는 에이전트에게 주기 좋은 도구다. 에이전트가 뭘 만들든 규칙 밖으로 못 나가고,
막히면 구조화된 조각으로 피드백을 받아 스스로 고칠 수 있다.
**구상만 있고 진입점은 없다** — 현재 진입점은 브라우저 화면뿐이다(4.3).

# 2부 — 거버넌스 모델

## 2.1 두 계층 통제: 어휘를 먼저 정하고, 규칙은 그 어휘만 참조한다

이 제품에서 규칙은 SQL 조각을 자유 입력으로 받지 않는다.

```
1단계  제약 사전    "이메일류 컬럼은 mask_email({col}) 형태로만 조회 가능"   ← 정의
2단계  컬럼 매핑    users.email → 그 정의                                  ← 적용
3단계  규칙         "이 매핑을 만족해야 한다"                              ← 참조만
```

**어휘를 먼저 정하고(1·2), 규칙은 그것을 참조만 한다(3).**
규칙 작성자는 새 표현을 만들 수 없고 등록된 어휘만 고른다. 이유는 셋이다.

- 오타·잘못된 형태가 규칙에 들어가지 못한다 (등록 시 파싱·형태 검증을 통과해야 한다)
- 같은 요건이 여러 규칙에 각자 다른 문자열로 복제되지 않는다
- 정의를 한 번 고치면 그것을 참조하는 규칙 전부가 같이 바뀐다

## 2.2 제약 6종

컬럼에 붙일 수 있는 제약은 여섯 가지다. 종류를 닫아 둔 것 자체가 통제다 —
새 종류를 추가하려면 "이것은 WHERE 요건인가" 같은 질문에 빠짐없이 답해야만 한다
(어떻게 강제하는지는 3.4).

| 종류 | 뜻 | 예 |
|---|---|---|
| **MASK** | 투영을 가려야 한다 | `email` → `mask_email(email)`로만 |
| **BLOCK** | 참조 자체 금지 | `ssn`은 SELECT·WHERE 어디에도 못 쓴다 |
| **FILTER** | 필수 조건 — **목적 범위를 가진다** | 마케팅 목적일 때 `consent_yn = 'Y'` |
| **INTEGRITY** | 필수 조건 — **목적과 무관하게 항상** | `deleted_at IS NULL` |
| **PARTITION** | 경계 조건이 있어야 한다 | `event_date`에 범위·등호·IN |
| **JOIN** | 조인 등식 요건 | 이 두 테이블은 이 키로만 이어야 한다 |

`FILTER`와 `INTEGRITY`를 가른 것이 이 모델에서 가장 늦게 배운 것이다.
둘 다 "WHERE에 있어야 하는 조건"인데 **목적 범위의 유무가 다르다.**
같은 종류로 두면 "삭제되지 않은 행만"이 목적별로 켜졌다 꺼졌다 한다.

## 2.3 목적(purpose) — 클라이언트가 고를 수 없다

"마케팅 분석", "고객 지원", "장애 조사" 같은 **조회의 목적**이다. 승인 요청서에 목적을 적고,
승인되면 그 요청으로 저장한 쿼리는 그 목적을 물려받는다.

목적별 `FILTER`는 목적이 일치할 때만 요구된다. 중요한 것은 **목적을 클라이언트가 못 고른다**는
점이다 — 저장·미리보기·실행 세 경로 모두 서버가 승인 요청서에서 목적을 꺼내 주입한다.
클라이언트가 목적을 고를 수 있으면 목적별 필터를 **스스로 면제**할 수 있기 때문이다.

(이 통제에는 서버 쪽 구멍이 남아 있다 — 4.1 첫 항목.)

## 2.4 판정하고 제안한다 — 서버는 사용자 SQL을 바꾸지 않는다

이 제품은 원래 **자동 재작성** 모델이었다. 사용자가 쓴 SQL에 서버가 마스킹 함수를 씌우고
필수 조건을 끼워 넣어 실행하는 방식이다. 재작성 엔진을 다 만들었고, 검증기까지 붙였다.

**그 모델을 버렸다.** 결정적인 실측 하나 때문이다.

> "동의한 사용자만" 필터를 `NOT EXISTS` 스코프에 주입하니, 결과가 정확히 **비동의자만** 남았다.
> 거버넌스가 보호하려던 모집단을 골라내는 도구가 됐다.
>
> — `ir/Ir.kt`, `injectable` 필드 KDoc

부정 문맥(`NOT EXISTS` / `NOT IN` / `NOT (...)`) 안에서 조건 주입은 필터를 **반전**시킨다.
스코프마다 극성을 따져 주입하는 것은 가능하지만, 그때 서버는 사용자가 의도하지 않은 쿼리를
실행하는 주체가 된다 — 그리고 그것이 맞는지를 판단할 근거는 서버에 없다.

지금 모델은 이렇다.

- **막는다.** 위반이면 저장도 실행도 안 된다.
- **조각을 준다.** 고친 SQL 전문이 아니라 **그 자리에 쓸 조각**이다(`mask_email(email)`, `consent_yn = 'Y'`).
- **사용자가 고친다.** 화면의 `[적용]`은 서버를 부르지 않고 에디터 텍스트만 고친다.
- **원문 그대로 실행한다.** 서버가 하는 재작성은 논리 테이블명 → 물리 테이블명 치환과 행 상한뿐이다.

부수 효과가 크다. **판정 대상과 실행 대상이 갈라질 자리가 대부분 사라졌다.**
재작성 모델에서는 "판정한 SQL"과 "실행한 SQL"이 다른 문자열이라, 그 사이를 지키는 장치
(재작성 검증기·스코프 난스·계획 대조)가 전부 필요했다. 그 장치들이 근거를 잃었다.
(완전히 사라진 것은 아니다 — 4.3 참조.)

## 2.5 fail-closed — 모르면 막는다

이 제품의 판정 계약에서 가장 중요한 문장은 이것이다.

**"모른다"와 "없다"를 같은 값으로 쓰면, 모르는 것이 전부 안전으로 읽힌다.**

그래서 판정 불가는 통과가 아니라 차단이다. 구체적으로:

- **파서가 구조로 표현하지 못한 조각은 어떤 요건도 충족시키지 못한다.**
  그 조각 때문에 요건 판정 자체가 불가능해지면 차단한다.
- **컬럼 귀속이 안 되면 미충족.** 다중 테이블 FROM에서 한정자 없는 컬럼이 어느 테이블 것인지
  확정할 수 없으면 요건을 못 채운 것으로 본다.
- **조인 종류를 모르면 양쪽 다 위험 목록에 넣는다.**
- **검사 자체가 실패하면 "검증 불가"로 보고한다.** 구조를 훑는 도중 예외가 나도
  "위반 없음"이 아니다. 빈 목록으로 보고하면 그것이 fail-open이다.
- **강제식을 해석할 수 없으면** 그 요건은 "검증할 수 없습니다"로 차단된다.

**비용은 과차단이다.** 판정할 수 없는 문법을 쓰면 정당한 쿼리도 막힌다. 이것을 감수하는 이유는
반대 방향의 실패(유출)가 조용하기 때문이다. 과차단은 사용자가 즉시 항의하지만, 유출은 아무도 모른다.

다만 **과차단도 측정한다.** 오탐 스위트가 따로 있고, 남은 과차단 3건이 테스트에 이름으로 고정돼 있다(4.2).

## 2.6 요건 충족의 판정 규칙

"조건이 있다"를 어떻게 인정하는지가 통제의 실체다. 닫힌 목록으로 정해져 있다.

- **최상위 AND 조건만 인정.** `WHERE consent_yn='Y' OR 1=1`은 미충족.
  `NOT (consent_yn='Y')`도, `consent_yn <> 'Y'`도 미충족.
- **INNER JOIN의 ON은 WHERE와 동치로 인정. OUTER JOIN의 ON은 인정하지 않는다** —
  LEFT JOIN의 ON은 행을 걸러내지 않기 때문이다.
- **모든 스코프에서 판정한다.** 루트뿐 아니라 서브쿼리·파생 테이블·CTE 본문·UNION 각 팔·
  `IN`/`EXISTS` 서브쿼리 전부. CTE 안에 숨기는 우회를 막는다.
- **귀속 단위는 테이블 이름이 아니라 FROM 안의 인스턴스(별칭)다.**
  셀프 조인 `user_events a JOIN user_events b`에서 `a.event_date=...`는 `b`의 요건을 못 채운다.
- **문자열 비교 금지.** 강제식은 파싱된 구조로 비교한다. 인정하는 동치는
  `=`의 좌우 순서, 식별자 케이스 정규화, `IN ('Y')` ≡ `= 'Y'` — 이 셋뿐이다.
- **경계는 모양이 아니라 사실로 본다.** `BETWEEN a AND b`만 인정하고 `>= a AND < b`를 막으면
  안전 방향이 거꾸로다 — 통과하는 BETWEEN이 1년이고 막히는 부등호 쌍이 1개월일 수 있다.
  그래서 "경계가 있는가"라는 **사실**을 묻는다.

## 2.7 관문은 둘 — 요청서 승인과 쿼리 검토

쿼리를 저장하려면 **승인된 요청서**가 있어야 하고, 그 요청서가 쿼리의 모든 물리 테이블을
덮어야 한다. 요청서에는 대상 테이블·목적·업무 사유·참조 규칙·승인선이 담긴다.

- **테이블은 카탈로그에 있는 것만** 담을 수 있다(자유 입력 금지). 권한 없는 테이블은 못 담는다.
- **순차 승인** — 단계마다 지정된 승인자 본인만 결정할 수 있고, 한 명이라도 반려하면 즉시 종료.
- **자가 승인 금지.** 요청자는 자기 요청의 승인자가 될 수 없다.
- **규칙 스냅샷.** 승인 시점의 규칙 트리를 통째로 저장한다 — 나중에 규칙이 바뀌어도
  "그때 무엇을 근거로 승인했는가"가 남는다. 현행 규칙과 달라지면 화면에 드리프트 배지가 뜬다.
- **승인 범위 우회 차단.** 커버 검사는 루트뿐 아니라 모든 자손 스코프의 물리 테이블을 재귀로 모은다.
  이게 없으면 `WITH x AS (SELECT ... FROM users) SELECT ... FROM x` 한 줄로 승인 범위를 벗어난다.
- **자격 검사가 상태 검사보다 앞선다** — 자격이 없으면 404로 존재 자체를 숨긴다.

그리고 **저장과 실행 사이에 관문이 하나 더 있다.** 저장된 쿼리는 `검토 대기` 상태로 들어가며,
거버넌스 담당이 **쿼리 검토**에서 승인해야 실행할 수 있다. 두 관문의 질문이 다르다 —
요청서는 "이 사람이 이 데이터를 볼 자격이 있는가", 쿼리 검토는 "이 SQL이 그 자격 안에 있는가".
쿼리를 수정하면 검토 상태가 초기화되고 다시 판정된다.

## 2.8 역할

| 역할 | 할 수 있는 것 |
|---|---|
| **ANALYST** | 쿼리 작성·저장·실행, 승인 요청 생성 |
| **STEWARD** | 위 + 카탈로그·규칙 편집, 쿼리 검토, 승인 결재, 전역 감사 조회 |
| **ADMIN** | 위 + 사용자 활성/비활성, 테이블 권한 편집 |

**역할 축과 데이터 접근 축은 별개다.** ADMIN이라고 해서 데이터 권한을 우회하지 않는다 —
테이블 접근은 별도의 권한 판정을 거치고, 등록되지 않은 테이블은 오타와 권한 부족을 구분해서
각각 다른 코드로 거부한다.

단, **모든 조회가 역할로 막히지는 않는다.** 사용자 목록·승인자 후보·목적 목록 등 몇몇 조회는
인증만 있으면 열린다(승인선 편성에 후보 목록이 필요해서 의도적으로 연 것과, 단순 누락이 섞여 있다 — 4.1).

## 3.1 전체 흐름

```

   │
   ▼
② 파싱 (Druid MySQL) → IR          거버넌스 전용 투영
   │
   ▼
③ 판정 (룰 엔진)                    시스템 룰 7종 + 사용자 규칙 트리
   │                                모든 스코프 순회 → 위반 + 고칠 조각
   ▼

   ▼
```

## 3.2 접수 검사 — 왜 IR이 아니라 원문에서 하는가

파싱하기 **전에** 원문과 어휘 스캐너로 거르는 층이 따로 있다. 왜 구조가 아니라 원문인지가 중요하다.

> IR은 lossy하다. MySQL 실행 주석(`/*!50000 UNION SELECT ssn FROM users */`)으로 감싼 UNION은
> IR에서 **전혀 보이지 않지만** MySQL은 그것을 실행한다.
>
> — `parser/SqlIntake.kt` KDoc

그래서 접수 검사는 두 겹이다. ⑴ **어휘층** — 주석·`FOR SHARE` 같은 것은 파싱 성공 여부와
무관하게 항상 검사한다. ⑵ **AST 방문자층** — 파싱된 구조에서 검사한다.

거부하는 것: 모든 주석, `INTO`/`FOR UPDATE`/`LOCK IN SHARE MODE`/힌트, 사용자·시스템 변수와
바인드 파라미터, 스키마 한정자, 물리 테이블 없는 조회(`FROM DUAL` 등),
금지 함수(`LOAD_FILE` `SLEEP` `BENCHMARK` `GET_LOCK` `FOUND_ROWS` 등 11종), `LIMIT` 오프셋.

식별자 비교는 **정규화 후에** 한다. 백틱 제거를 빠뜨리면 `` `sleep` ``이 금지 목록을 통째로
무효화한다 — 실제로 그렇게 뚫린 적이 있다.

**자원도 유계로 만든다.** API 접수 상한 60,000 B(파서 자체 상한은 64 KiB), 이진 연산자 체인 상한,
파싱 깊이 상한 100. 깊이 상한을 정한 근거가 남아 있다.

> 상한은 스택 용량이 아니라 **정상 쿼리가 필요로 하는 만큼**으로 잡는다.
> 상한이 스택 용량에 가까우면 **계수기가 세기 전에 스택이 먼저 터진다**
> (실측: 1000은 뚫렸고 200은 잡혔다). 실제 쿼리의 파싱 깊이는 **2**다.
>
> — `parser/BoundedMySqlParser.kt` KDoc

Druid 파서의 재귀 지점 두 곳에 깊이 계수기를 끼운 서브클래스로 구현했다.
남의 라이브러리를 재구현하지 않고 이음매만 잡은 것이다.

## 3.3 IR — 왜 직접 만들었나

**IR**(중간 표현, Intermediate Representation)은 SQL 전체를 표현하지 않는다.
**거버넌스에 필요한 것만 담은 투영**이다.

```
QueryIR
 └ SelectScope(kind, tables, selectItems, whereConjuncts, columnRefs,
               joinEqualities, limit, children, unverifiable, ...)
     ScopeKind = ROOT | SUBQUERY | DERIVED | CTE | UNION_ARM | EXISTS
```

설계에서 중요한 두 가지.

**⑴ 컬럼 참조는 "어디에 어떤 형태로"가 아니라 "참조했다는 사실"만 담는다.**
그래서 select·WHERE·GROUP BY·HAVING·ORDER BY·JOIN ON·함수 인자·CASE 전부를 방문자 하나로 덮는다.

**⑵ 절을 손으로 나열하지 않는다.** 실제로 그렇게 만들었다가, 목록 밖 문법 셋
(`USING`, `NATURAL JOIN`, 명명 `WINDOW`)의 컬럼 참조가 표시 없이 사라졌다. 그중 하나는 실제 유출이었다.
원인은 하나였다 — **컬럼 참조를 수집할 절 목록을 손으로 나열했고 MySQL 문법이 그보다 넓었다.**

> 열거의 누락은 **조용하다**. 예외도 로그도 없고, 검사기가 "없다"고 정직하게 답한다.

수정 방향은 기본값을 뒤집는 것이었다. "적은 것만 검사"에서 **"전부 훑고 뺄 것만 뺀다"**로,
그리고 뺄 때는 이유를 적는다.

**직접 만든 것이 맞았나?** `docs/adr/001`에 Apache Calcite 스파이크 실측이 있다. 요약하면:

- 우리가 겪은 결함 5종이 Calcite 관계대수에서는 **생기지 않는다**(`USING`을 등식으로 펼치고,
  `NATURAL JOIN`은 공통 컬럼 전부를 펼치고, CTE는 인라인되어 "겹 경계" 개념 자체가 없다)
- 그러나 우리 룰 7종 중 `no-select-star`는 **표현 불가**하다 — 별이 컬럼 목록으로 펼쳐져
  "별을 썼다"는 사실이 사라진다
- 그리고 **관계대수로 가면 원문을 잃는다**(별칭 소실, CTE 인라인). 제안을 원문에 앵커링해야 하는데.

> **정규화 이득은 관계대수에, 원문 보존은 AST에 있다. 한 경로로 둘 다는 안 된다.**
>
> — `docs/adr/001-sql-ir-build-vs-buy.md`

결론은 **유지하되 재검토를 예약**. 전환점은 멀티 벤더다 — 방언이 늘면 문법 전수 대조를
방언마다 다시 해야 하고, 그 비용이 도입 비용을 넘는 지점이 온다.
그리고 **이제 이주를 잴 수 있다** — SQL 형태 76개가 기대값으로 고정돼 있어서,
엔진을 갈아끼우고 그 표가 초록이면 동작 보존의 증거가 된다.

## 3.4 룰 엔진 — 두 채널

**시스템 룰 7종**은 코드로 박혀 있다.

| 룰 | 등급 | 하는 일 |
|---|---|---|
| `no-select-star` | BLOCK | `*`·`t.*` 금지 (`COUNT(*)`와 `EXISTS` 안은 면제) |
| `no-blocked-column` | BLOCK | BLOCK 제약 컬럼 참조 금지 |
| `must-be-masked` | BLOCK | MASK 컬럼은 강제식 형태로만 |
| `require-predicate` | BLOCK | FILTER·INTEGRITY 요건 충족 |
| `require-partition-key` | BLOCK | 파티션 컬럼에 경계 조건 |
| `require-limit` | WARN | 루트에 행 상한 |
| `unknown-table` | WARN | 카탈로그에 없는 테이블 |

**사용자 규칙**은 데이터다. AND/OR 트리에 조건을 달고, **조건 단위로** 등급을 준다.
연산자는 `requires` / `blocks` / `joins` / `must_be_masked` 넷이 판정 대상이고,
`must_be_within`은 등록·표시만 하고 판정하지 않는다.

두 채널의 결과는 **순수 합집합**이다. 한쪽이 다른 쪽을 억제하지 않는다.

제약 종류를 늘릴 때 실수를 막는 장치가 여기 있다. "이 종류는 WHERE 요건인가"라는 질문을
망라적 분기 한 곳에 모아 두어서, **새 종류를 추가하는 사람이 그 질문에 답해야 컴파일된다.**
근거가 코드에 적혀 있다.

> 세 곳에 `kind == FILTER`를 흩어 놓았던 것이 사고의 원인이었다: 판정만 FILTER를 보고
> 주입은 FILTER+INTEGRITY를 봐서, **INTEGRITY의 유일한 강제 수단이 실행 시점 주입**이 되어 있었다.
> […] `else`를 두면 새 종류가 조용히 "요건 아님"으로 분류되고,
> 그것이 바로 방금 고친 사고의 모양이다.
>
> — `catalog/CatalogEntities.kt`, `DefKind.isRequiredPredicate` KDoc

설계에서 볼 만한 것 둘:
- **손상된 규칙은 격리된다** — 파싱 안 되는 규칙 트리는 평가에서 빼고 목록에 `corrupt`로 표시.
  평가를 통째로 죽이지도, 조용히 넘기지도 않는다.
- **위반 메시지와 제안 조각이 같은 값에서 나온다.** 갈라질 자리를 안 만든다.

## 3.5 실행 게이트 — 순서를 타입으로 강제한다

실행 경로는 11단계다.

```
가시성 → 본인 실행 → 파싱 → 권한 → 승인 → 판정 → 매핑 → 계획 → 재작성·검증 → 행 상한 → 실행
```

미리보기는 실행과 **같은 사슬**을 쓰되 마지막 두 단계(행 상한·실행)가 없다.
**저장 게이트만 순서가 다르다** — 승인 검사가 판정보다 뒤에 온다.
그 순서가 4.1의 "판정 오라클"을 만든다.

### 단계 증거 사슬

각 단계는 다음 단계가 요구하는 **증거 타입**을 발급한다. 모든 단계가 새 타입을 만들지는 않는다 —
다음 단계가 요구할 때만 발급한다.

```
Parsed → Authorized → ApprovalCovered → Judged<Prior> → Mapped → Planned → Ready → Executable
```

`Judged<out Prior : Authorized>`가 제네릭인 이유는 하나다 —
**입력이 무엇이었는지가 결과 타입에 남는다.**
실행은 `Judged<ApprovalCovered>`를 얻고 저장은 `Judged<Authorized>`를 얻는데,
매핑 단계가 `Judged<ApprovalCovered>`를 요구하므로 **승인 검사를 건너뛴 판정으로는 실행 사슬에
컴파일이 되지 않는다.** 순서를 주석이 아니라 컴파일러가 지킨다.

### 발급 권한 폐쇄

증거를 손으로 조립하면 위 장치가 무의미하다. 그래서 발급을 닫았다.
Kotlin에 friend 가시성이 없어 **범위가 다른 두 장치를 겹쳤다.**

- `sealed` → **패키지** 단위 제약 (파일 아님 — 이걸 처음에 틀리게 적었다)
- `private` 최상위 선언 → **파일** 단위 제약

전용 패키지 `query.gate`를 만들고, 구현체를 발급자와 같은 파일에 `private`로 두었다.
결과: 그 패키지에 발급 함수를 가진 파일이 하나뿐이라, **전 단계의 전이 함수만 다음 타입을 발급한다.**

한계도 코드가 적어 뒀다 — 소스 수준 폐쇄라 리플렉션은 못 막는다.
목표는 "평범한 코드가 실수로 게이트를 건너뛰는 것"을 컴파일 오류로 만드는 것이다.

### 실패는 예외가 아니라 값

차단은 `GateStop`이라는 **값**이다. 5변종이 각각 자기 감사 코드를 안다.
이유가 두 개 적혀 있다.

> 예외는 **호출자의 트랜잭션을 롤백시키는 side-effect**를 갖는데, 게이트에는 되돌릴 쓰기가 없다.
> 그리고 차단은 예외 상황이 아니라 **이 제품의 정상 결과**다.
>
> — `query/gate/GateStop.kt` KDoc

예전에는 같은 개념이 한 함수 안에서 네 문법으로 쓰였다(try/catch·지역 클로저·5인자 함수·`runCatching`).
그중 하나를 빠뜨려 **403인데 감사 0건**인 경로가 있었다.

**문법의 다양성이 누락을 숨겼다.**

## 3.6 실행 격리

**3중이다.**

1. **별도 스키마** — 실행 대상은 `queryguardian_demo`, 설정 DB는 `queryguardian`.
2. **별도 계정** — `REVOKE ALL PRIVILEGES` 후 `GRANT SELECT`만. FILE·PROCESS·SUPER 없음.
   `EXECUTE`는 스키마 전체가 아니라 **마스킹 함수 3개에 개별로** 부여했다 —
   나중에 루틴이 추가돼도 자동으로 포함되지 않게. 마스킹 함수는 `SQL SECURITY INVOKER` 필수
   (생략하면 definer가 root가 된다).
3. **매핑표의 총체성** — 논리 테이블명 → 물리 테이블명 매핑이 **전부** 있어야 실행된다.
   부분 매핑을 허용하면 미매핑 테이블이 원래 이름으로 실행돼
   `SELECT tree_json FROM rule` 같은 실재 거버넌스 테이블을 직격한다.

**읽기 전용도 3중** — 계정 권한 + 커넥션 풀 `readOnly` + 커넥션마다 `SET SESSION TRANSACTION READ ONLY`.

**`sql_mode`를 두 번 틀렸다.** 이 기록이 남아 있다.

> 처음엔 전체를 갈아써서 서버 기본값의 `ONLY_FULL_GROUP_BY`가 사라졌고 —
> 검토자가 승인한 SQL이 실행 시점에 그룹당 임의 행을 고르는 **다른 의미**로 돌았다.
> 그래서 합집합으로 바꿨더니 이번엔 `ANSI_QUOTES`가 **상속**됐다:
> 판정기는 `"ssn"`을 문자열 리터럴로 보는데 실행 세션은 **컬럼 참조**로 읽어,
> BLOCK 등급 컬럼이 차단을 통과해 원문으로 나갈 수 있었다.
>
> — `exec/QueryExecutor.kt` KDoc

지금은 금지 모드 5종(`NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES`, `PIPES_AS_CONCAT`, `IGNORE_SPACE`,
`HIGH_NOT_PRECEDENCE`)을 제거하고 **다시 읽어 확인**한 뒤, 남아 있으면 실행하지 않는다.

**행 상한**은 `min(사용자 LIMIT, 설정 상한)`을 SQL에 주입하되 `+1`로 건다.
`maxRows+1`번째 행이 오는지로 "더 있는가"를 확정한 뒤 그 행을 버린다.
드라이버의 `setMaxRows`는 쓰지 않는다 — **상한 장치가 둘이면 어긋난다.**
`LIMIT 0`도 존중한다(0을 "미지정"으로 보면 0행 요청이 상한만큼 반환된다).

## 3.7 감사 — 결과 행은 남기지 않는다

**결과 행은 어디에도 저장되지 않는다.** 감사 테이블에 rows 컬럼이 **아예 없다** — 행 수만 있다.
타입·스키마 수준에서 저장이 불가능하고, 통합 테스트가 이력 문자열에 이메일이 없음을 단정한다.

남는 것: 결말, 원본 SQL, 재작성된 SQL, 서버가 적용한 재작성 목록(테이블 치환·행 상한),
행 수, 소요 시간, 상한 3값(설정 상한 / 실제 적용 / 더 있는가), 오류 코드·원문, 행위자, 시각.

**감사는 실행 경로에만 남는다.** 저장 게이트와 lint는 같은 차단 코드를 응답으로 내보내되
감사 행을 남기지 않는다 — 실행이 아니기 때문이다.

**등급이 둘이다.** 이것이 이 설계의 중심이다.

- **반출이 있는 종결**(성공·미리보기) — **기록이 반출의 선행 조건**이다.
  감사 기록에 실패하면 결과를 내보내지 않는다.
- **반출이 없는 종결**(차단·오류) — 기록은 best-effort. 원래 사유가 이기고, 유실은 경보로 남긴다.

미리보기가 "반출" 등급인 이유: 미리보기 응답은 **적용해야 할 강제식의 형태**를 조각으로 담으므로
카탈로그 오라클이다.

감사 코드를 enum이 아니라 문자열로 저장한 이유도 적혀 있다.

> 감사는 **append-only 이력**이다 — 어휘에서 코드 하나를 지우는 순간 enum이면
> 그 값을 가진 옛 행을 **읽을 수 없게 된다**. 이력을 읽지 못하게 만드는 통제는 통제가 아니다.
>
> — `exec/ExecutionAudit.kt` KDoc

또 하나: **전역 감사 조회 경로가 저장 쿼리와 분리돼 있다.** 쿼리를 지워도 전역 감사에는 남는다.
커서 페이징이라 "새 기록을 쌓아 옛 기록을 조회 범위 밖으로 밀어내는" 우회도 막힌다.
(다만 소유자의 쿼리별 이력은 쿼리가 지워지면 못 본다 — 4.3.)

**DB 수준 강제는 없다**(4.1).

## 3.8 검증 전략

이 저장소에서 가장 특이한 부분일 수 있다.

**⑴ 우회 스위트 / 오탐 스위트를 따로 둔다.** 우회 16건, 오탐 9건.
같은 누락도 **실패 방향에 따라 심각도가 다르다** — 금지 룰의 누락은 유출이고 요건 룰의 누락은
과차단이다. 한 숫자로 세면 안 된다.

**⑵ 형태 커버리지 76개.** "이 SQL은 이렇게 판정되어야 한다"를 기대값으로 고정한 표.
엔진 교체의 안전망이자, 어떤 문법이 판정 사각인지의 지도다. 과차단으로 남은 3건은
`KNOWN_OVERBLOCK`에 이름으로 박혀 있다 — 고쳐지면 그 자리가 빨간불로 알려 준다.

**⑶ 감사 코드 전수 검증.** 감사 코드 20종 각각에 대해 **실제 HTTP 요청**을 보내
감사 1행·결말·행위자·상태 코드·응답 본문 코드까지 단정한다. 열거 항목에 기본값을 안 두어서,
"코드 없는 종결"을 새로 만들면 **컴파일이 실패한다.**
(20종 중 8종은 정상 입력으로 도달할 수 없어 내부 실패를 강제해서 태운다. 그 한계도 적어 뒀다 —
판정이 재작성과 같은 기준을 쓰는 한 재작성 거부 코드는 2선 방어다.)

**⑷ 구조 감시자.** 계층 경계 6종(Druid는 파서 밖으로 못 나가고, 판정 경로는 인증을 모르고,
IR이 유일한 공용 어휘고, 감사 어휘는 아무것도 의존하지 않는다) + 게이트 접근 3종
(실행기는 게이트만 부를 수 있고, 실행 증거는 어떤 필드에도 저장되지 않는다).

**⑸ 감시자 자신을 시험한다.** 이 습관이 가장 값졌다.

- **감시자마다 되돌려 실패**를 확인한다 — 잡아야 할 것을 심어 빨간불이 켜지는지.
- 그것으로 부족하다. **감시자가 KDoc으로 약속한 범위의 경계 밖에도 심어 본다.**
  실제로 리플렉션 기반 감시자가 companion 함수 한 줄에 뚫렸다 — 네 테스트를 전부 통과했다.
- **허용 오차와 완료 기준도 잰다.** 시각 회귀의 1% 허용 오차가 1280×900에서 약 11,500픽셀이라
  사이드바가 모든 화면에서 밀린 변경을 삼켰다. 재 보니 실제 잡음 바닥은 0이었다.
- 왕복 테스트의 완료 기준("위반이 전부 사라졌다")이 **위반이 둘 이상인 쿼리를 추가 불가능하게**
  만들고 있었다. 세는 것은 정직했는데 표본이 이미 좁혀져 있었다.

**자를 만들 때 그 자가 무엇을 못 재게 만드는지 함께 묻는다.**

# 4부 — 정직한 한계

이 절이 있는 이유: 이 저장소는 "무엇을 막는다"를 근거 없이 쓰는 것을 반복된 실수로 기록해 왔다.
그래서 막지 못하는 것을 같은 문서에 적는다.

> 이 문서의 초안도 같은 실수를 했다. 적대 검증이 **강한 단정 8건의 반례**를 찾았고
> 그 대부분이 이 절에 반영돼 있다. 낡은 인덱스에서 옮겨 온 숫자 넷도 여기서 걸렸다.

전체 목록은 `.dev/BACKLOG.md`에 사유와 착수 순서까지 있다.

## 4.1 지금 새는 곳

- **목적 통제에 서버 쪽 fail-open이 있다.** 판정 함수의 목적 인자에 기본값이 있어서,
  호출부가 목적을 빠뜨려도 컴파일이 통과하고 **목적별 요건이 0건 발화**한다.
  2.3이 내세우는 통제가 클라이언트에 대해서만 닫혀 있다.
  → *왜 아직인가*: 기본값 제거 + 목적을 값 타입으로 올리는 작업이 호출부 전체를 건드린다.

- **목적 밖 값 유출.** 사용자 규칙 채널이 목적 범위 밖에서도 강제식 값을 조각에 실어 보낸다.
  시스템 룰 채널은 침묵하는데 사용자 규칙 쪽은 말한다.
  → *왜 아직인가*: 판정 경로에 목적 필터를 걸면 **판정까지 좁아져 fail-open**이 된다.
  조각 생성에만 걸어야 하고, 그러려면 평가기 시그니처를 바꿔야 한다.

- **전역 스코프 규칙은 아무것도 막지 않는다.** 규칙에 단일/다중/전역 범위를 줄 수 있는데,
  전역으로 등록한 규칙은 평가에서 **통째로 제외**된다. 화면이 배지로 알리기는 한다.
  → *왜 아직인가*: 범위 축을 실제 평가에 연결하는 설계 결정이 필요하다.

- **화면이 `must_be_masked`를 "판정 미구현"이라고 표시한다.** 백엔드는 판정하고 차단하는데
  규칙 편집 화면은 미강제라고 말한다. **화면이 틀린 말을 하고 있다.**
  → *왜 아직인가*: 이번 검증에서 처음 발견됐다.

- **제약 수정 경로가 등록 검사를 지나간다.** 등록 시 하는 형태 검증이 **수정** 경로에는 없다.
  요건을 마스킹으로 바꾸면 요건이 조용히 사라진다.
  → *왜 아직인가*: 담당자 권한 안이고 원래부터 있던 구멍.

- **항등 마스킹을 등록할 수 있다.** `CONCAT({col}, '')`을 마스킹 강제식으로 등록하면
  검증을 전부 통과하고 평문이 나가는데 감사에는 정상 실행으로 남는다.
  → *왜 아직인가*: 프로브 값 검사만으로는 증명이 안 된다(가역 인코딩·부분 항등 함수가 통과한다).
  허용 함수 목록이나 비가역성 계약이 필요하다.

- **감사가 코드로 지워진다.** 리포지토리가 표준 인터페이스라 삭제 메서드가 상속으로 열려 있고,
  DB 트리거·권한 회수는 0건이다. 코드가 스스로 적어 뒀다 —
  *"지금 그런 호출자가 없다는 것은 규약이지 컴파일 보장이 아니다."*

- **새 목적에 제약이 안 붙는다.** 목적별 제약의 기본이 "적용 안 함"이라, 목적을 새로 만들면
  아무 제약도 없는 상태로 시작한다. 안전하려고 목적별로 등록했다가 새 목적에서 조용히 빠진다.

- **판정 오라클.** 남의 요청서 번호를 넣어 저장을 시도하면 **그 사람의 목적 기준으로 판정된
  보고서**를 받는다. 저장 게이트에서 룰 판정이 승인 검사보다 앞에 오는 구조적 결과다.

- **인증만 있으면 열리는 조회들.** 사용자 목록·승인자 후보·업무 요건 목록·목적 목록에
  역할 검사가 없다. 앞의 셋은 승인선 편성에 후보 목록이 필요해 **의도적으로 연 것**이고,
  목적 목록은 단순 누락이다.

## 4.2 알려진 과차단

- **남은 과차단 3건**이 테스트에 이름으로 고정돼 있다. 전부 **겹 경계**에서 멈추는 형태다 —
  CTE 안의 테이블에 대한 조건이 바깥에 있으면 합산하지 못한다(사용자 규칙 축 포함).
  방향은 안전하지만 **쿼리를 읽기 좋게 쪼개면 막히고 한 줄로 뭉치면 통과**해서 나쁜 스타일을 유도한다.
- **정당한 예외를 표현할 길이 없다.** "소프트 삭제된 행을 봐야 하는 복구 작업"이 그냥 막힌다.
  방향은 정해 뒀다 — 요청서가 **어느 규칙으로 조회할지 고른다**(면제가 아니라 선택).
  안전은 다른 데서 온다: 기본은 엄격한 쪽 / 고를 수 있는 건 등록된 것만 / 고른 사실이 승인 대상.
- **CTE·파생·UNION 팔 안의 위반에는 고칠 조각을 못 준다.** 화면의 적용기가 텍스트 조작이라
  스코프를 짚을 수 없어서다. 조각을 주려면 적용기가 파서가 돼야 한다.

## 4.3 구조적 한계

- **CI가 없다.** 구조 감시자·리플렉션 검사는 누군가 테스트를 돌릴 때만 발화한다.
  컴파일러로 올릴 수 있는 것은 전부 올렸지만, 남은 감시자들은 이 사실 위에서 읽어야 한다.
- **MySQL 단일 방언.** 방언이 늘면 문법 전수 대조를 방언마다 다시 해야 한다.
- **에이전트용 진입점이 없다.** 판정 결과가 구조화돼 있어 API로 노출하면 되지만,
  현재 진입점은 브라우저 화면뿐이다(1.4⑸).
- **화면 일부가 고정 스텁이다.** 에디터의 AI 패널과 데이터베이스 화면의 테이블 메타·인덱스는
  디자인 샘플이 그대로 들어 있다. "화면 8종"이 전부 실 데이터는 아니다.
- **`no-select-star`는 텍스트/AST 층에만 존재한다.** 관계대수로 이주하면 이 룰을 잃는다.
- **판정과 실행이 갈라질 자리가 완전히 닫히지는 않았다.** 파싱 결과의 구조와 실행 핸들이
  같은 파싱에서 나왔다는 것을 타입이 보장하지 못한다. 오늘은 생성 지점이 하나뿐이라 위험이 낮지만,
  **캐싱 계층이 생기면 다시 봐야 한다.**
- **재작성 검증기가 테이블 집합 동등성을 단정하지 않는다.** 매핑 총체성은 게이트 단계에서
  성립하지만, 검증기 층은 독립적인 기대치를 만들지 않는다. 3.6이 말하는 셋째 겹에 2선 방어가 없다.
- **오류 원문 노출 정책의 판정지가 둘이다.** 쿼리별 이력과 전역 감사가 각각 판정한다.
  느슨해지는 방향은 아니지만 **조여도 절반만 적용된다.**
- **소유자가 자기 실행 이력 창구를 잃을 수 있다.** 쿼리가 삭제되면 쿼리별 이력은 404가 된다
  (전역 감사는 담당자 전용).
- **다중 인스턴스 `USING`의 가드가 측정되지 않았다.** 가드를 느슨하게 바꿔도 전체 테스트가 통과한다
  = 그 경우를 태우는 형태가 없다. 그 가드의 근거는 논증이지 측정이 아니다.
- **규칙의 "적용 범위"가 실제 범위가 아니다.** 화면은 단일/다중/전역으로 제시하는데
  평가는 대상 테이블 참조만 본다(전역은 위에 적은 대로 아예 평가되지 않는다).
- **미결 정책** — 담당자가 남의 저장 쿼리를 지울 수 있다. 삭제는 파괴적 쓰기인데
  *열람* 능력으로 통과한다. 현행을 테스트로 고정해 두었으므로, 정책을 정하면 그 테스트가 먼저 실패한다.

# 5부 — 이 저장소가 일하는 방식

코드만큼이나 **과정 자체가 자산**으로 관리된다. 위에 인용한 실측·반례는 전부 그 산물이다.

모든 작업이 6단계 루프를 돈다:
**구조 점검 → 맥락 이해 → 계획·승인 → 실행 → 검증 → 회고·자산화.**

- 계획은 **파일로** 남는다 (`docs/spec/NNN-*.md`). 사람이 검토하고 승인한 뒤에 실행한다.
- **자가검증을 피한다.** 검증은 서브에이전트나 타사 모델에게 맡기되,
  **축을 갈라서 붙인다** — 보안·정합성 채널과 설계 품질 채널이 별개다.
  섞으면 늘 보안이 이겨서 설계 결함이 전부 통과한다(실측).
- 회고는 `.dev/retrospect/`, 배운 것은 `.dev/learning/`, 그리고 각각 **한 줄 후크 인덱스**를 유지한다.
  다음 작업에서 통독 대신 한 줄로 상기할 수 있어야 회고가 복리가 된다.
- 결정의 **근거는 코드 주석에 남긴다.** 이 문서의 인용 대부분이 KDoc에서 나왔다.
  그래서 이 저장소에서는 **거짓말하는 주석이 자산을 깎는다.**
  (이 문서 자체가 그 위험의 사례다 — 낡은 인덱스에서 옮긴 숫자 넷이 검증에서 걸렸다.)

읽을 만한 자리:

| 파일 | 무엇 |
|---|---|
| `docs/spec/INDEX.md` | 스펙 13편의 한 줄 요약 + 상태 |
| `docs/spec/001-mvp-scope.md` §6 | fail-closed 판정 계약 7항 — 이 제품의 실체 |
| `docs/adr/001-sql-ir-build-vs-buy.md` | IR을 직접 만든 이유 + Calcite 스파이크 실측 |
| `.dev/learning/INDEX.md` | 배운 것 21편의 한 줄 요약 |
| `.dev/BACKLOG.md` | 미해결 목록 — 사유와 착수 순서 포함 |

규모: 백엔드 65파일 · 테스트 42파일 · 화면 8종.

## 실행

```bash
cd docker && docker compose up -d          # 설정 DB (MySQL 8, 3307)
cd backend && ./gradlew bootRun            # 백엔드 (8080)
cd frontend && npm install && npm run dev  # 프론트 (5180)
```

http://localhost:5180 → 카탈로그에서 테이블·제약·목적 등록 → 에디터에서 쿼리 작성.

```bash
cd backend && ./gradlew test    # 단위 + 우회/오탐 스위트 + Testcontainers 통합 (docker 필요)
cd frontend && npm run build    # 타입 체크 + 번들
cd frontend && npx playwright test
```
