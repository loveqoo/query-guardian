# ADR 001 — SQL IR: 직접 만들 것인가, Apache Calcite를 쓸 것인가

- **일자**: 2026-07-27
- **상태**: 제안 (사용자 검토 대기)
- **관련**: spec 008 §0 정정 · spec 011 · retrospect 019 · learning 020

## 맥락

이 제품의 메인 기능은 **IR을 통한 룰 통제**다. 지금 IR(`SelectScope`·`ColumnRef`·`TableRef`·
`whereConjuncts`·`joinEqualities`)은 Druid 파서의 AST에서 직접 만든 **거버넌스 전용 투영**이다.

사용자가 물었다: *"SQL에 대한 IR 계산을 지원하는 라이브러리가 있나요? 직접 만드는 게 맞나요?"*
저장소에 이 선택을 기록한 문서가 **없었다** — 그래서 이 ADR을 만든다.

계기는 2026-07-27의 우회 조사다. 실제 유출 3종(`USING`·`NATURAL JOIN`·`WINDOW`)을 찾았고
원인이 하나였다 — **컬럼 참조를 수집할 절 목록을 손으로 나열**했고 MySQL 문법이 그보다 넓었다.
열거는 빠뜨리는 쪽으로 실패하고 그 실패는 조용하다(learning 020).

## 검토한 선택지

| 후보 | 성격 | 판단 |
|---|---|---|
| **Apache Calcite** | 파서 + 검증기 + **관계대수 IR** + 옵티마이저 (Java) | 직접 후보 — 아래 스파이크 대상 |
| ZetaSQL | 엄격한 이름 해소 (C++/JNI) | JVM 결합 비용 과다 |
| Trino·Spark 분석기 | 엔진 내장 플래너 | 엔진에 결합, 무거움 |
| JSqlParser · Druid | **파서일 뿐 IR 아님** | 현행(Druid)과 같은 층 |
| sqlglot | 파서 + 계보 (Python) | 언어 불일치 |
| Substrait | IR **포맷**(생산자 아님) | 생산자가 여전히 필요 |

## 스파이크 결과 (실측, 2026-07-27)

격리 프로젝트에서 Calcite 1.37로 확인했다. 실험 코드는 저장소에 없다.

### 우리가 겪은 결함이 그쪽에서 생기는가 — **안 생긴다**

| 우리 결함 | Calcite 관계대수 |
|---|---|
| `JOIN b USING (ssn)` 미인식 | `LogicalJoin(condition=[=($1, $7)])` — ssn 등식으로 펼침 |
| `NATURAL JOIN` 미인식 | 공통 컬럼 **6개 전부**의 등식으로 펼침(스키마를 알기 때문) |
| `WINDOW w AS (ORDER BY ssn)` 미인식 | `ROW_NUMBER() OVER (ORDER BY $1)` — 인라인 해소 |
| 개명 사슬 추적 | 출력 컬럼 원본이 `users.ssn`으로 되짚힘 |
| **겹 경계에서 멈춤**(`F2`) | CTE가 인라인되어 **겹 개념 자체가 없음** — 그냥 된다 |

마지막 줄이 크다. spec 011 Q3(이 스펙에서 가장 위험한 변경)이 그쪽에서는 **공짜**다.

### 우리 룰을 표현할 수 있는가 — **7종 중 6종**

- **인스턴스 키(셀프 조인 분리) 가능** — 두 스캔이 서로 다른 원본으로 나오고, 더 견고하게는
  **입력 서수 경계**로 갈린다(`$1`=왼쪽, `$4`=오른쪽). 우리가 별칭으로 손수 하던 것을 구조가 대신한다.
- **`no-select-star`는 표현 불가** — 별이 컬럼 목록으로 펼쳐져 "별을 썼다"는 사실이 사라진다.
  파싱 단계(SqlNode)에서만 보인다.
- `unknown-table`은 검증기 **예외**가 된다(`ValidationException`, 메시지에 테이블명). 값으로 바꾸려면
  사전 조회나 메시지 파싱이 필요하다 — 깔끔하지 않다.
- **미측정**: `must_be_masked`의 투영/비투영 구분, purpose별 술어, `H6`·`K4`.

### 원문 보존 — **관계대수로 가면 잃는다**

```
원문   : SELECT c.id FROM user_events c JOIN users u ON c.id = u.id WHERE ...
되생성 : SELECT `user_events`.`id` FROM `user_events` INNER JOIN `users` ON ...   ← 별칭 c·u 소실
원문   : WITH t AS (...) SELECT id FROM t
되생성 : SELECT `id` FROM (SELECT ...) AS `t`                                     ← CTE 인라인
```

**검증만 거친 AST는 원문을 유지한다**(별칭·CTE 보존, 한정자만 추가). 그러나 그 단계에서는
`USING`·`NATURAL`·명명 윈도가 **그대로 남는다** — 정규화 이득이 없다.

> **정규화 이득은 관계대수에, 원문 보존은 AST에 있다. 한 경로로 둘 다는 안 된다.**
> 다만 **파서 하나로 두 관점**은 가능하다: 판정=RelNode, 제안=검증된 SqlNode.

## 결정

**당분간 직접 만든 IR을 유지한다.** 다만 **재검토를 예약**한다.

이 결정을 지금 뒤집지 않는 이유:

1. **판정 계층 전체를 다시 써야 한다** — 시스템 룰 7종 + 사용자 규칙 평가기. 도메인 로직의 대부분이다.
2. **룰이 세 층으로 나뉜다** — 원문 텍스트(접수 검사) / SqlNode(`no-select-star`) / RelNode(나머지).
3. **미측정 항목이 남아 있다**(위 목록).

재검토를 예약하는 이유:

1. **spec 008 §0 정정으로 원문 보존의 근거가 약해졌다.** 서버가 사용자의 SQL을 바꾸지 않는다면
   "재작성 결과를 보여주려고 원문을 지킨다"가 사라지고, **제안을 앵커링하는** 용도만 남는다.
2. **멀티 벤더(②)가 전환점이다.** 방언이 늘면 문법 전수 대조를 방언마다 다시 해야 하고
   (백로그 항목), 그 비용이 도입 비용을 넘는 지점이 온다.
3. **이제 이주를 잴 수 있다.** `ShapeCoverageTest`의 형태 55개가 "이 SQL은 이렇게 판정되어야 한다"를
   기대값으로 고정한다. 엔진을 갈아끼우고 이 표가 초록이면 동작 보존의 증거가 된다.
   **이 안전망이 없었다면 이주를 안전하게 시도할 수 없었다.**

## 지금 가져올 것

전면 이주 없이 얻을 수 있는 것 하나: **`NATURAL JOIN`을 거부 대신 펼칠 수 있다.**
지금은 파서가 카탈로그를 몰라 "조인 키를 알 수 없다"며 거부한다(`unverifiable-scope`).
카탈로그는 컬럼 목록을 아니까, 판정 계층에서 공통 컬럼을 계산해 등식으로 펼치는 길이 있다.
**거부가 유일한 답은 아니었다.**

## 이 ADR이 없었던 대가

이 선택은 기록 없이 내려졌고, 그래서 오늘 사용자가 물을 때까지 아무도 다시 보지 않았다.
그동안 우리는 라이브러리가 이미 푼 문제(표기 정규화·컬럼 원본 추적·술어 전파)를 **손으로
재발견하며 고쳤다**. 다음 근본 선택은 착수 **전에** ADR을 남긴다.
