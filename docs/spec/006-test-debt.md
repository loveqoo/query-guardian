# 006 — 테스트 부채 상환

> 상태: **완료** (테스트 전용 단위, 프로덕션 동작 변경 없음)
> 작성: 2026-07-25 · 근거: retrospect 005(spec 004 갭), retrospect 006(spec 005 갭)
> 2라운드에 걸쳐 "코드엔 반영했으나 전용 테스트가 없는" 항목이 누적됐다. 기능 추가 전에 상환한다.

## 1. 목표

적대 검토가 지적해 **코드로는 막았지만 테스트로 고정되지 않은** 경로를 회귀 스위트로 확정한다.
테스트가 없으면 다음 리팩터가 조용히 되돌릴 수 있다(특히 fail-closed 경로).

## 2. 상환 목록

| # | 출처 | 항목 | 기대 동작 | 유형 |
|---|---|---|---|---|
| T1 | spec 004 H3 | 판정 불가 형태(`<>` 등)를 requires 조건으로 참조 | 규칙 등록 **400** | 통합 |
| T2 | spec 004 H6 | tree_json 손상·미지 op | 해당 규칙만 격리(corrupt=true), 다른 규칙·시스템 룰 정상 | 통합 |
| T3 | spec 004 C4 | **컬럼 삭제로 매핑이 연쇄 삭제된 뒤** 규칙 조건이 dangling | 평가기 **fail-closed 차단**(조용한 통과 금지) | 통합 |
| T4 | spec 005 C4 | 같은 단계 **동시 승인** 2건 | 하나만 200, 나머지 409 (단계 미증가) | 통합(동시) |
| T5 | spec 005 H2 | 승인 후 규칙 트리 편집 | 요청 상세의 `changedSinceApproval=true` | 통합 |
| T6 | spec 005 C6 | 저장 후 BLOCK 규칙 추가 → 검토 승인 시도 | **409**(재-lint 차단) | 통합 |

주: T3은 매핑 삭제 API가 아니라 **테이블 수정(컬럼 제거) 경로**를 쓴다 — 이 경로는 spec 005의 역참조
가드(409)를 우회해 매핑을 연쇄 삭제하므로, dangling이 실제로 발생 가능한 유일한 경로다.

## 3. 검증 기준

- [x] T1~T6 신규 테스트 전부 통과
- [x] 기존 95개 테스트 회귀 통과(프로덕션 코드 변경 없음이 원칙 — 테스트가 결함을 드러내면 그때만 수정)
- [x] 결함 발견 시: 수정 + 사유를 이 문서 §4에 기록

## 4. 발견된 결함 (실행 중 기록)

- (T3) 컬럼 삭제로 매핑이 사라지면 `RequirePredicateRule`은 카탈로그에서 술어가 사라져 **위반을 발생시키지
  않는다**(요구 자체가 소멸). 반면 **사용자 규칙 조건은 defId를 직접 참조**하므로 dangling이 되고,
  `UserRuleEvaluator`가 fail-closed로 차단한다 — 즉 시스템 룰과 사용자 규칙의 dangling 반응이 다르다.
  이는 설계상 의도(카탈로그 = 요구의 출처, 규칙 = 명시적 참조)이므로 **문서화**하고 테스트로 고정한다.

## 5. 결과

T1~T6 신규 7건 전부 통과, 기존 95건 회귀 통과(**합계 102건**). **프로덕션 코드 변경 0** —
부채 항목들이 실제로 "코드는 맞고 테스트만 없던" 상태였음이 확인됐다. 특히:
- T3: 컬럼 삭제로 dangling된 사용자 규칙 조건이 실제로 fail-closed 차단됨(조용한 통과 아님).
- T4: 동시 승인 2건 중 정확히 1건만 성공하고 current_step이 1만 증가(건너뛰기 없음) — @Version 낙관적 잠금이 실동작.
- T2: 손상 규칙이 격리돼도 lint가 죽지 않고 정상 규칙 판정은 그대로 발화.
