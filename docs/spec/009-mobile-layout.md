# 009 — 모바일 레이아웃 대응

> 상태: **승인 (2026-07-25 사용자)**
> 작성: 2026-07-25 · 근거: 사용자 요청(모바일에서 보기 어려움), spec 003(디자인 컨버팅), learning 006(디자인 충실도)
> spec 008 M3(실행 결과 화면) **앞에** 진행한다 — 그래야 M3 UI가 처음부터 반응형으로 올라간다.

## 1. 목표와 경계

**목표**: 휴대폰(360~430px 폭)에서 7개 화면을 **읽고 조작할 수 있게** 한다.

**경계 — 데스크톱은 픽셀 단위로 불변이다.** 원본 `dc.html`이 유일한 디자인 원본이고(spec 003),
시각적 동일성이 1차 수용 기준이다(learning 006). 이 스펙은 **원본이 다루지 않는 뷰포트**에 대한 추가 정책이며,
데스크톱 폭에서는 토큰·간격·배치가 한 픽셀도 바뀌지 않아야 한다.

**비목표**: 모바일 전용 화면 신설, 정보 구조 변경, 터치 제스처, PWA·오프라인.

## 2. 측정된 현재 상태 (코드 기준, 추측 아님)

| 항목 | 현재 | 모바일 영향 |
|---|---|---|
| 사이드바 | `width={236}` 상시 표시 | 390px의 60% 점유 |
| 셸 높이 | `height: 100vh` + `overflow: hidden` | iOS 주소창으로 하단 잘림, 페이지 스크롤 불가 |
| flex 행 | 163개 중 wrap 23개 | 대부분 찌그러짐·가로 넘침 |
| 에디터 | 최상위 2단 flex + 고정 폭 컨트롤(150·170·250px) | 가로 넘침 |
| antd 반응형 API | 사용 0건 | 전부 고정 레이아웃 |
| 표 | `<Table>` 2개, `scroll={{x}}` 0개 | 표가 뷰포트를 밀어냄 |
| 콘텐츠 패딩 | 24px | 좁은 화면에서 낭비 |

## 3. 방침

**한 곳에서 끊는다.** 163개 flex 행을 각각 손보는 대신, 브레이크포인트 하나와 전역 규칙 몇 개로 대부분을 덮고,
그래도 깨지는 화면만 개별 손질한다. 화면마다 다른 방식으로 반응하면 유지보수가 불가능해진다.

- **브레이크포인트: 992px**(antd `lg`). 이하를 "좁은 화면"으로 본다. antd `Grid.useBreakpoint()`를 쓴다.
  *(초안의 768px에서 고쳤다 — 실측 결과 768px에서도 사이드바 236px를 빼면 내용이 532px뿐이어서 다열 그리드가
  그대로 넘쳤다. 기준은 뷰포트 폭이 아니라 **사이드바를 뺀 내용 폭**이다.)*
- **셸**: 사이드바를 `Drawer`로 전환(헤더에 햄버거), 헤더 압축, 콘텐츠 패딩 24 → 12.
- **높이**: `100vh` → `100dvh`(동적 뷰포트) + 모바일에서는 페이지 스크롤 허용.
- **전역 안전장치**(CSS 한 곳): `body`는 **절대 가로 스크롤하지 않는다**. 넓은 것(표·코드·다이어그램)은
  각자 `overflow-x: auto` 컨테이너 안에서만 스크롤한다.
- **표**: `scroll={{ x: "max-content" }}`로 가로 스크롤. 카드형 변환은 하지 않는다(디자인 이탈 + 비용).
- **2단 → 1단**: 에디터·승인·규칙의 좌우 분할을 모바일에서 세로 스택. 고정 폭 컨트롤은 `width: 100%`로.

## 4. 마일스톤

| # | 산출물 | 완료 기준 |
|---|---|---|
| 1 | 셸 반응형(Drawer 내비·헤더·패딩·`100dvh`) + 전역 가로 스크롤 금지 | 390px에서 모든 화면이 가로 스크롤 없이 열린다 |
| 2 | 화면별 스택 전환(에디터·승인·규칙·카탈로그·DB·저장쿼리·관리) | 각 화면의 주요 조작이 390px에서 가능하다 |
| 3 | 표·코드 블록 가로 스크롤 격리 | 표가 뷰포트를 밀지 않는다 |
| 4 | 데스크톱 회귀 확인 | 1280px에서 spec 003 대비 시각 변화 0 |

## 5. 결정 기록 (2026-07-25 사용자)

1. **모바일에서도 편집을 허용한다** — 레이아웃만 세로 스택하고 에디터는 그대로 쓴다. 오타 수정·짧은 손질은
   모바일에서도 실제로 필요하므로 막지 않는다.
2. **Playwright를 개발 의존성으로 추가해 시각 회귀를 자동화한다** — 여러 뷰포트에서 렌더링해 스냅샷을 대조한다.
   근거: "데스크톱 픽셀 불변"은 눈으로 확인할 수 없는 종류의 약속이다. 코드 diff만으로는
   "브레이크포인트 밖에서 아무것도 안 바뀌었다"를 증명할 수 없다(전역 CSS 한 줄이 전 화면을 바꿀 수 있다).

**작업 순서상 중요한 점**: 변경 **전에** 기준 스냅샷을 찍는다. 그래야 데스크톱 스냅샷이 그대로 통과하는 것이
불변의 증거가 되고, 모바일 스냅샷 변경은 의도한 것만 남는다.

## 5.5 실기기 피드백으로 드러난 것 (2026-07-25)

첫 라운드를 "가로 넘침 0"으로 마쳤는데 사용자가 실기기에서 **"컬럼이 보이지 않는다, 모든 메뉴에서 컴포넌트가
렌더링이 잘 안 된다"**고 지적했다. 원인은 **높이**였고, 내 검증에 두 개의 사각이 있었다.

1. **폭만 측정했다.** 데스크톱은 "뷰포트 높이를 나눠 갖는 패널"이 각자 내부 스크롤한다. 그 구조를 좁은 화면에서
   세로로 쌓으면 패널마다 한 조각만 보인다 — 실측: 컬럼 표 컨테이너가 **높이 79px에 내용 861px**.
   → 좁은 화면에서는 `height: 100%`·`min-height`·내부 세로 스크롤·`flex: 1`을 모두 내용 높이로 바꾼다.
   스크롤 주체는 페이지(main) 하나여야 한다.
2. **스크린샷이 첫 화면만 담았다.** 앱이 `main` 안에서 스크롤하므로 Playwright의 `fullPage`가 화면 아래쪽을
   담지 못한다 — 결함이 정확히 그 사각에 있었다. → `mobile-tall`(390×2000) 프로젝트를 추가해 아래쪽까지 담는다.

같은 라운드에서 내 전역 규칙이 만든 부작용도 실측으로 잡았다: `min-width: 0`이 **버튼을 폭 2px로** 짜부라뜨렸다
(누를 수 없다) → 버튼·태그는 축소 대상에서 제외하고, 대신 행을 줄바꿈시킨다.

**검증에 추가한 지표**: 내용이 눌린 컨테이너(`scrollHeight > height + 40`)가 0이어야 한다.
폭 지표만으로는 이 결함이 통과했다 — 사용자가 볼 수 있는 것과 지표가 어긋나면 지표를 고쳐야 한다.

## 6. 검증

- **가로 넘침은 측정한다** — 각 화면에서 `documentElement.scrollWidth <= clientWidth`를 단정한다.
  "보기 어렵다"는 감각을 객관 지표로 바꾸는 유일한 방법이고, 모바일 깨짐의 대부분이 이 하나로 드러난다.
- **데스크톱 회귀는 스냅샷으로** 막는다(1280px 프로젝트가 변경 없이 통과해야 한다).
- 실기기 확인은 마지막 관문이다 — 실제 기기는 사용자 쪽에 있고, 헤드리스는 근사치다.
- 이 스펙은 백엔드를 건드리지 않는다 → 백엔드 테스트 223건은 무관(변경 없음을 diff로 확인).
