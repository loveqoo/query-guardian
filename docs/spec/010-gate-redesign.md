# 010 — 실행 게이트 재설계: 단계 증거 + 값 기반 실패

> v3 (2026-07-26) — 검토 3라운드(사용자 리뷰 → 사내 적대 2건 → codex) 반영 · **재검토 대기**
> 검토 이력과 v1·v2의 결함은 `.dev/retrospect/013-gate-redesign-review.md`.
> 현행 코드 결함 D-A~D-F는 `.dev/BACKLOG.md`(이 재설계와 별개로 열려 있다).

## 1. 진단

**순서가 정책인데 그 순서가 타입에 없다.** 그래서 절차를 두 번 적었고(`execute`/`previewRewrite`가
~85% 중복), 실패를 여섯 갈래로 내보냈고, 설계 의도를 타입 대신 주석에 적었다.

## 2. 불변식

| # | 불변식 |
|---|---|
| I1 | 게이트 순서는 **단일 정의**를 갖는다. 진입점이 늘어도 순서를 다시 적지 않는다 |
| I2 | 단계 증거는 **위조할 수 없다** — 각 단계 타입은 전 단계의 전이 함수만 발급하고, 밖에서 생성하거나 구현할 수 없다 |
| I3 | 게이트의 실패는 **한 종류의 값**이며 감사 코드·사유·감사 페이로드를 필수 필드로 싣는다. 응답 코드 == 감사 코드 |
| I4 | **반출이 있는 종결(SUCCESS·PREVIEW)은 감사 기록이 반출의 선행 조건이다.** 기록하지 못하면 내보내지 않는다 |
| I5 | **반출이 없는 종결(BLOCKED·ERROR)은 기록이 best-effort**이며 기록 실패가 원래 사유를 덮지 않는다. 단, 기록 실패 자체가 **경보 대상**이다 |
| I6 | 게이트 경로는 **트랜잭션을 열지 않는다.** 유일한 쓰기는 감사이며 자기 트랜잭션(`REQUIRES_NEW`)을 갖는다 |
| I7 | 게이트 본문·단계 함수는 예외를 **만들지도 잡지도 않는다.** 실패는 값이다. 예외 취급은 경계에만 있다 |
| I8 | 성립하지 않는 상태 조합은 **타입으로 표현 불가**하다(권한 재확인 없는 판정, 계획 없는 실행, 핸들 없는 재작성) |
| I9 | **실행은 증거 토큰 소지로만** 가능하다. 토큰은 actor·대상·purpose·판정 AST 난스·승인 상태에 결합되고 **단회성**이다 |
| I10 | **실행기는 게이트 밖에서 호출할 수 없다** |
| I11 | 감사의 append-only는 **DB 권한으로 강제**된다 — 애플리케이션 관례가 아니다 |
| I12 | 파싱은 **자원이 유계**다: 동시 실행 수 · 대기열 · 벽시계 · **잔존 작업** 넷 모두 |
| I13 | enum은 경계에서만 문자열이 된다. 도메인 안에서는 enum이다 |

I4·I5는 나란히 읽어야 한다. v2는 여기에 "모든 종결에 감사 1행"을 적었다가 모순을 냈다 — best-effort는
존재성을 보장하지 않는다. **불변식은 소원이 아니라 사실이어야 한다.**

기존 불변식은 그대로 유효하다: 결과 행 미저장, 부분 적용 없음, fail-closed, 판정과 실행의 문법 일치,
대행 실행 불허(008 결정 14), purposeCode 서버 주입(008 C1).

> **용어**: "단일 파싱"은 *판정과 재작성이 같은 AST를 쓴다*는 뜻이지 요청당 파서 호출 1회가 아니다.
> `RewriteVerifier`의 재파싱은 독립 이중 방어이며 유지한다 — 호출 횟수를 세는 검사를 만들지 말 것.

## 4. 설계

### 4.1 단계 증거 (I1·I2·I8)

**분할 기준: 후속 단계가 요구하는 보안 증거 단위로 쪼갠다.** 개수와 이름은 구현 자유다.
"감사 코드가 갈리면 쪼갠다"(v2)는 기준은 틀렸다 — 코드가 같아도 순서가 중요한 검사가 있고,
순서와 무관한데 코드만 다른 검사도 있다.

**본체는 필드가 아니라 발급 권한이다**(I2). 각 단계 타입은 ⑴ 밖에서 생성할 수 없고 ⑵ 밖에서 구현할 수
없으며 ⑶ **전 단계의 전이 함수만** 다음 타입을 발급한다. 이것이 없으면 증거 객체를 조립해 순서를 건너뛸 수
있고, 그 순간 I1·I8은 문서상의 주장으로 되돌아간다.

상태 누적을 어떻게 표현할지(위임·중첩·단일 불변 컨텍스트 + 최소 증거)는 **구현 자유**다. 요구는 둘:
마지막 단계가 15개 인자를 나르지 않을 것, 그리고 `parse=Success`와 AST 핸들이 **한 타입 안에서**
non-null로 묶일 것(`inspected.statement!!` 소멸).

방언은 단계 타입의 제네릭으로 올리지 않는다 — 올리면 레지스트리가 스타 프로젝션이 되어 캐스트가
되돌아온다. 방언 짝은 런타임 검증(`ParsedStatement.dialect` + scopeId 난스)으로 지킨다.

**거처**: 단계 타입과 실패 타입은 `query`(게이트) 패키지. `ir`에 두면 ArchUnit `irIsTheSharedVocabulary`가
깨진다. 실패 타입은 도메인 `LintReport`를 싣는다(`api.LintReportDto`를 실으면 `query ↔ api` 순환).
ArchUnit 추가: `query`는 `api`를 의존하지 않는다.

### 4.2 진입점 — 부분 개방 (I9)

| 훅 | 상태 |
|---|---|
| SQL 출처 · 감사 귀속 | **열림** (실행하는 의도는 `queryId` non-null 강제) |
| 검토 승인 요구 · purpose 출처 · 종결(실행 여부) | **닫힘** — 실행은 증거 토큰 소지 조건이고, `Purpose`는 `ApprovalRequest`에서만 생성되는 타입이다 |

v1은 진입점을 열린 축에 두었다. 그러면 새 클래스 하나로 결정 4·C1·결정 14가 동시에 소멸한다 —
각 칸에 미리보기라는 전례가 있어 리뷰에서 이상해 보이지도 않는다.

**공유 훅**(두 진입점이 반드시 함께 통과): 길이 → 파싱 → 데이터 권한 재검사 → 승인 커버 재검사 →
접수·룰 재판정 → 데모 매핑 총체성 → 계획 → 재작성 → 재작성 검증. A1은 이 목록을 복제해 검사하지 않고,
**두 진입점이 같은 파이프라인을 쓴다는 사실 자체**를 검사한다.

### 4.3 실패는 값이다 (I3·I6·I7)

`sealed interface GateStop { val code: AuditCode; val status: HttpStatus; val audit: AuditPayload }`.
단계 전이는 성공/차단을 한 타입으로 반환하고, **조합자 하나**가 단축을 담당한다 — `when`은 조합자 안에
한 번 있고 줄기에는 없다. 선례가 집 안에 있다: `spring-jpa-kraft`의 `core/ResultExtensions.kt`가
`flatMap`/`zip`을 손으로 구현하고 `FormResolver.toEntity()`는 한 줄로 읽힌다.

**예외 기반 비지역 반환을 쓰지 않는 이유**: 예외는 호출자의 트랜잭션을 롤백시키는 side-effect를 갖는다.
게이트에는 되돌릴 쓰기가 없으므로(I6) 그 효과는 이득이 아니라 **우리가 통제하지 않는 경계에 남기는
레버**다 — 나중에 배치·에이전트가 게이트 호출을 자기 트랜잭션으로 감싸면 차단이 그쪽 쓰기를 조용히
되돌린다. 또한 차단은 예외 상황이 아니라 **이 제품의 정상 결과**다.

`sealed`가 망라성을 준다는 주장은 거짓이다(`when`을 직접 쓸 때만이고 `else`·맵 조회면 통과한다).
강제는 **추상 멤버 3개**와 `sealedSubclasses` 순회 테스트가 한다. `AuditCode`는 enum이며 모든 이름이
32자 이하임을 테스트로 고정한다(`error_code VARCHAR(32)`).

**arrow-kt는 도입하지 않는다.** 도메인 실패 타입 + 조합자 하나가 이 집의 기존 패턴이고, arrow가 더 주는
것은 현재 범위에서 `raise` 지점의 비지역 반환뿐이다 — 그것은 유틸 사용이다.
**재도입 조건**: `LintReport`를 `EitherNel<Violation, T>`로 바꿔 접수·룰·승인 위반을 한 어휘로 누적할 때.
그때 arrow는 유틸이 아니라 모델이 된다. (v2가 든 철회 근거 중 "참조 저장소의 arrow 사용은 한 함수뿐"과
"트랜잭션 롤백 위험"은 부정확했다 — 상세는 retrospect 013.)

### 4.4 예외의 거처 (I7)

경계에서만 예외를 다룬다: 파서 · JDBC · 리포지토리. 클래스 개수는 구현 자유이나 **이름이 지정되어야**
한다(A3가 그 목록으로 검사한다). 파서 경계는 `StackOverflowError`를 포함한 재귀 폭주도 실패 값으로
번역하며, **두 위치를 따로 다룬다** — 문자열 파싱(별 스레드 → `ExecutionException`)과 IR 구성(호출
스레드 → 직접 `Error`)은 실패 형태가 다르다.

### 4.5 감사 (I4·I5·I11)

| 종결 | 반출 | 기록 | 실패 시 |
|---|---|---|---|
| SUCCESS · **PREVIEW** | 있음 | 선행 조건 | **반출하지 않는다** |
| BLOCKED · ERROR | 없음 | best-effort | 원래 코드로 응답 + **경보** |

PREVIEW가 SUCCESS와 같은 등급인 이유: 미리보기 응답은 **적용될 강제식 원문**을 담는 카탈로그 오라클이다.
데이터 행이 없다고 반출이 아닌 것이 아니다.

**인프라 실패도 종결이다.** `ExecutionFailure`(타임아웃·SQL 오류)는 `GateStop`의 한 변종으로 흡수하며
`outcome = ERROR`·`rewrittenSql`·`applied`를 페이로드에 싣는다. "인프라 예외는 잡지 않는다"를 무조건
규율로 두면 이 경로의 감사가 조용히 사라진다.

`AuditPayload`는 `originalSql`을 non-null로 요구한다(`original_sql`은 NOT NULL). "열람 권한 없음이라
본문을 기록하지 않는다"는 전용 변종 `Redacted`로 **타입에 적는다** — 주석이 아니라.
`SUCCESS`의 의미는 **"실행이 끝나 결과를 만들었다"** 이지 HTTP 전달 성공이 아니다(동기 HTTP에서 후자는
보장할 수 없다). 감사 기록이 프록시 경계를 지나 `REQUIRES_NEW`로 열린다는 사실은 자기호출로 깨지므로
소스 규율로 고정한다.

### 4.6 스프링이 이미 주는 것

`Actor`를 인자 해결기로 주입해 시그니처에서 `actor: String`을 걷고, `privileged: Boolean` 플래그를 능력으로
바꾼다 — **실행 소유권 면제 능력은 정의조차 하지 않는다**(없는 능력은 잘못 쓸 수 없다).
엔티티 필드를 enum으로 바꾼다(I13; 커스텀 컨버터 필요 여부는 **미확인** — 필드 타입 변경만으로 되는지 먼저 확인).
오류 바디에는 **`code`를 추가**한다. 바디 통합은 프론트 계약 3종을 깨므로 이 스펙에서 하지 않는다.

### 4.7 파서 자원 유계 (I12)

`cancel(true)`는 순수 CPU 파싱을 멈추지 못하고 `newCachedThreadPool`은 무제한이다. 그러나 그것이
게이트의 **유일한 벽시계 가드**이기도 하므로 없애기만 해서는 안 된다. 요구는 넷이며 구현 형태는 자유다:
**동시 실행 수 유계 · 대기열 유계(포화 시 거부는 `GateStop`) · 벽시계 유계 · 잔존 작업 유계**.
마지막 항목이 핵심이다 — 취소 불가한 작업이 worker를 영구 점유하면 이후 정상 SQL이 계속 거부된다.
입력 형태 상한(중첩 깊이·토큰 수)은 **보조** 수단이며, 계산 규칙(UTF-8 바이트·인용 식별자·평면 부울
체인)을 명시해 오차단을 만들지 않는다.

### 4.8 null 정리 범위

단계 타입이 `statement!!`를 없애고, `norm`을 두 정의역으로 갈라 12곳을 없애고,
`parsePredicate(): Predicate?`를 타입 실패로 바꾼다. 엔티티 id의 `!!` 21개는 5개 패키지에 흩어져 있어
**이 스펙에서 걷지 않는다** — 증가만 막고 별도 스펙으로 분리한다.

### 4.9 확장 축 — OCP

**변하는 축은 열고 정책인 축은 닫는다.** 닫힌 축의 확장점은 곧 우회점이다.

| 축 | 상태 | 강제 |
|---|---|---|
| 방언 | 열림 | 레지스트리 빈. 단계 타입은 방언 제네릭을 갖지 않는다 |
| 재작성 종류 | 종류 열림 / **적용 순서 닫힘** | 순서는 `RewriteKind`가 정한다. `List<T>` 주입 순서는 비결정적이다. 기동 시 중복·미커버 검사 |
| 룰 연산 | 평가자 열림 / **커버리지 닫힘** | 기동 시 전수 확인 + **op별 적대 계약 테스트**(구현체가 항상 빈 결과를 반환해도 fail-open이다) |
| 감사 1차 저장 | **닫힘** | 동기·필수. I4가 여기 붙는다 |
| 감사 부가 포워딩 | 열림 | 1차 저장 성공 후에만. `originalSql`·`rewrittenSql`·`applied`·`error_detail` 모두 민감하므로 전달 필드·보존·암호화를 계약에 적는다 |
| 마스킹 강제식 | 열림 + **증명 의무** | 프로브 값 비교로는 부족하다(프로브만 다르게 반환하는 `CASE`·가역 인코딩이 통과). **허용 함수 allowlist** 또는 비가역성 계약 |
| 진입점 | 부분 개방 | §4.2 |
| 단계 순서 · `GateStop` 사유 · 실행 격리 · 금지 `sql_mode` · 실행기 접근 | **닫힘** | I10 포함 |

**열린 축의 증명 의무는 "자기 검증"이 아니다.** 기대치를 자기 계획에서 뽑는 검증은 `RewriteVerifier`가
이미 실패 모드로 실증한 형태다. 기대치는 **닫힌 전역 정책 모델**이 판정 IR + 카탈로그에서 산출하고
전역 검증기가 계획과 대조한다. 이 요구는 미래 확장뿐 아니라 **기존 FILTER·TABLE_MAP·LIMIT·INTEGRITY에도
적용된다** — 오늘은 마스킹만 독립 재도출이고 나머지는 계획만 순회한다(D-F).

## 5. 단계

| P | 내용 | 종료 조건 |
|---|---|---|
| **P0** | 안전망 — 감사 코드 enum + 전수 검증(A0), spec 008 §5 순서를 코드 기준으로 정정 | A0 |
| P1 | 실패 타입 + 조합자 + 경계 + 감사 두 등급 + 오류 바디 `code` + **파서 자원 유계** | A2·A3·A5·A7 |
| P2 | 단계 증거 도입 → 줄기 재작성, 중복 제거, 증거 토큰 | A1·A4·A6 |
| P3 | enum·`Actor` 능력·null 정리 | A8 |

**P0이 먼저인 이유**: 감사 코드 14종 중 오늘 테스트가 단정하는 것은 3개다. 그 상태의 247건은 안전망이 아니다.
**P1은 "동작 동일"이 아니다** — `code` 추가, 감사 실패 시 응답 변경, 인프라 예외 흡수는 관찰 가능한
의미 변경이다. 호환 변경과 의도적 변경을 커밋에서 분리한다.
A6은 P2 종료 조건이다(토큰이 P2에 도입되므로 그때부터 우회가 가능해진다).
테스트를 고쳐야 한다면 **그 테스트가 무엇을 지키고 있었는지 먼저 적는다.**

## 6. 하지 않는 것

기능 추가 없음(**M3은 이 재설계 뒤로**). IR·카탈로그·룰 **모델** 변경 없음. arrow·코루틴 없음.
ktlint · 오류 바디 통합 · 엔티티 id `!!` 일괄 정리 · 감사 DB 권한 조정(I11 이행) 은 각각 별도.

## 7. 위험

1. **감사 기록 지점이 바뀐다** → A0·A2·A5가 감시자.
2. **P3이 보안 경계를 만진다**(플래그 → 능력) → A6.
3. **분할의 양방향 실패** — 과소분할이면 순서가 규율로 남고, 과분할이면 상태 누적이 새 산만함이 된다.
4. **P1이 파서 격리를 손댄다** — 벽시계 가드와 `Error` 번역을 함께 옮기지 않으면 무기록 500이 생긴다.
