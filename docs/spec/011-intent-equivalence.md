# 011 — 의도 동치 판정 (요건 룰을 모양이 아니라 사실로)

> **이 스펙은 완화다.** 지금까지의 수정(`b29047b`·`94cacc1`)은 강화였고 틀려도 과차단이 늘 뿐이었다.
> 여기서는 요건을 **더 쉽게 충족**시킨다 — 틀리면 **누락차단**, 즉 유출이다.
> 이 저장소는 오차단 급수정으로 fail-open을 만든 적이 있다(retrospect 010).

## 1. 문제

`ShapeCoverageTest` 55형태 중 **과차단 5건**이 남아 있고 뿌리는 **둘**이다(실측).

| 뿌리 | 형태 | 엔진이 못 보는 사실 |
|---|---|---|
| **조각을 합쳐 보지 않는다** | `G1` `G5` | 부등호 둘이 하나의 경계를, OR 분기들이 같은 값을 만든다 |
| **겹을 이어 보지 않는다** | `F2` `H6` `K4` | CTE 안 테이블과 바깥 조건이 같은 쿼리다 |

증상은 하나로 보인다: **같은 의도를 다르게 쓰면 판정이 달라진다.**

```sql
event_date BETWEEN '2026-01-01' AND '2026-12-31'   -- 통과 (1년)
event_date >= '2026-01-01' AND event_date < '2026-02-01'  -- 차단 (1개월, 더 좁다)
```

## 2. 왜 지금 하는가

메인 기능이 "IR을 통한 룰 통제"다. 우회가 없어도 **정당한 쿼리가 막히면 제품이 아니다.**
그리고 대가가 안전 쪽도 아니다:

- 사용자가 **"허용되는 표기"를 추측**하게 된다. 그 추측은 우회를 익히는 것과 같은 학습이다.
- 쿼리를 **읽기 좋게 쪼개면 막히고 한 줄로 뭉치면 통과**한다 → 나쁜 스타일을 유도한다.
- 파티션 요건은 방향이 **거꾸로**다 — 넓은 `BETWEEN`이 통과하고 좁은 부등호 쌍이 막힌다.

## 3. 설계 원칙

**⑴ 사실을 넓히되 판정 기준은 좁힌다.** 요건 룰이 "이 조건문이 `BETWEEN` 모양인가"가 아니라
**"이 컬럼에 상한과 하한이 있는가"** 를 묻게 한다. 모양을 열거하면 또 빠뜨린다(learning 020).

**⑵ 완화마다 악용 형태를 먼저 추가한다.** 이 완화로 *새로 통과하게 되는* 쿼리 중
요건의 목적을 달성하지 못하는 것을 형태로 만들어 **누락차단 후보로 먼저 등록**한다.
안전망이 없는 완화는 하지 않는다(learning 015).

**⑶ 확신할 수 없으면 완화하지 않는다.** 현행(과차단)이 안전한 방향이다. 애매한 경우를 남기는 것이
잘못 여는 것보다 낫다 — 남은 과차단은 백로그이고, 잘못 연 것은 유출이다.

## 4. 불변식

| # | 불변식 | 왜 |
|---|---|---|
| I1 | 요건 충족은 **모든 행에 대해 참인 사실**에서만 나온다 | 일부 행에만 걸리는 조건은 스캔을 줄이지도, 데이터를 좁히지도 않는다 |
| I2 | 조각 합산은 **최상위 AND conjunct 집합** 안에서만 한다 | `OR` 아래의 조각을 합치면 `OR 1=1`류 무력화가 되살아난다 |
| I3 | `OR`는 **모든 분기가 그 컬럼을 고정할 때만** 충족으로 센다 | 한 분기라도 고정하지 않으면 그 분기의 행은 제약 없이 나온다 |
| I4 | 겹 잇기는 **의미 보존이 확실한 경우에만** 한다(§5.3 목록) | 집계·DISTINCT·LIMIT·표현식이 끼면 바깥 조건은 안쪽 조건과 다른 것이다 |
| I5 | 완화가 적용된 판정은 **그 근거를 메시지에 남긴다** | "왜 통과했는가"를 감사자가 재구성할 수 있어야 한다 |

## 5. 범위

### 5.1 조각 합산 — 파티션 (`G1`)

컬럼별로 최상위 conjunct에서 **사실**을 모은다: 하한 / 상한 / 등호 / 열거.
파티션 요건은 **"고정되었는가"** 를 묻는다 — 등호·열거·(하한∧상한) 중 하나.

| 형태 | 지금 | 이후 | 근거 |
|---|---|---|---|
| `= 'X'` | 통과 | 통과 | 고정 |
| `IN (…)` | 통과 | 통과 | 열거로 고정 |
| `BETWEEN a AND b` | 통과 | 통과 | 상·하한 |
| `>= a AND < b` | **차단** | **통과** | 상·하한 — `BETWEEN`과 같은 사실 |
| `>= a` 단독 | 차단 | 차단 | 상한 없음 = 사실상 전체 스캔 |

### 5.2 `OR` 분배 (`G5`) — ⚠️ 사람의 결정 필요

```sql
WHERE (event_date = '2026-01-01' AND id > 0)
   OR (event_date = '2026-01-01' AND id < 0)
```

**논리적으로는 건전하다**: 모든 분기가 그 컬럼을 고정하면 전체가 고정된다(I3). 값이 분기마다 달라도
(`d='X' OR d='Y'`) `IN ('X','Y')`와 같으므로 안전하다. 한 분기라도 고정하지 않으면(`d='X' OR id>0`)
미충족이다.

**그런데 경계가 붙어 있다.** 지금 막고 있는 술어 무력화(`consent_yn='Y' OR 1=1`)와 같은 문법이고,
`OR` 안쪽을 신뢰하기 시작하는 첫 자리다. 필수 술어(`requires`)에도 같은 논리를 적용할지는 별개 결정이다.

**결정 항목**: ⓐ 파티션·필수 술어 모두 적용 ⓑ 파티션만 적용 ⓒ 적용하지 않음(현행 유지).
결정 전까지 `G5`는 `KNOWN_OVERBLOCK`에 남긴다.

### 5.3 겹 잇기 (`F2`·`H6`·`K4`) — 가장 위험

CTE·파생 테이블은 인라인되므로 바깥 조건이 안쪽 테이블의 조건일 수 있다. 그러나 **항상 그런 것은 아니다.**
아래 **전부**를 만족할 때만 바깥 조건을 안쪽 요건 판정에 쓴다:

1. 안쪽 겹이 **단순 투영**이다 — 집계·`GROUP BY`·`DISTINCT`·`LIMIT`·`UNION`이 없다
   (있으면 행 집합이 바뀌어 바깥 조건이 안쪽 조건과 다른 것을 거른다)
2. 문제의 컬럼이 **직접 투영**이다 — `event_date` 또는 `event_date AS d`(개명은 추적).
   `DATE(event_date) AS d` 같은 **표현식이면 제외**한다(값이 다르다)
3. 바깥 조건이 그 별칭에 대한 **최상위 conjunct**다(I2)
4. 안쪽 겹이 **널 생성 쪽이 아니다** — OUTER JOIN의 보존되지 않는 쪽이면 제외
   (spec 008 §3.0.2가 주입에 대해 세운 것과 같은 이유)

그 외는 현행 과차단을 유지한다(원칙 ⑶).

## 6. 하지 않는 것

- **금지 룰(차단·마스킹)은 손대지 않는다.** 그쪽은 이미 정규화 기반이고, 완화할 이유가 없다.
- 옵티마이저 수준의 일반 predicate pushdown을 구현하지 않는다 — §5.3의 네 조건이 전부다.
- `SINGLE`/`MULTI`·`server` 미사용 문제(백로그)는 별개다.

## 7. 수용 기준

| # | 기준 | 재는 방법 |
|---|---|---|
| A1 | **누락차단 0 유지** | `ShapeCoverageTest` — 완화 전후 모두 |
| A2 | 악용 형태를 **완화보다 먼저** 등록했다 | 커밋 순서로 증명(빨간불 먼저) |
| A3 | 과차단 5 → 0(또는 `G5` 결정에 따라 1) | `KNOWN_OVERBLOCK` |
| A4 | 완화마다 **되돌려 실패** | 장치별로 하나씩 |
| A5 | 적대 검증 2채널(보안·정합성 / 설계 품질) | 축 분리 |
| A6 | 실서버 재확인 | 인메모리 픽스처 ≠ 실제 규칙·카탈로그 |

### 7.1 악용 후보 (A2 — 완화 전에 형태로 등록한다)

| 형태 | 왜 막혀야 하는가 |
|---|---|
| 집계 뒤 조건 — `WITH a AS (SELECT id, COUNT(*) c FROM user_events GROUP BY id) SELECT … WHERE …` | 집계 후 조건은 스캔을 줄이지 않는다 |
| 표현식 개명 — `SELECT DATE(event_date) AS d …` 후 바깥에서 `d = '…'` | 값이 다르다. 안쪽 컬럼을 고정하지 못한다 |
| `LIMIT` 낀 CTE | 안쪽이 이미 잘린 뒤라 바깥 조건은 다른 것을 거른다 |
| UNION 일부 팔만 조건 | 조건 없는 팔이 전체 스캔이다 |
| `OR` 한 분기만 고정 | 나머지 분기의 행은 제약이 없다 |
| OUTER JOIN 널 생성 쪽 | 조건을 밀어넣으면 조인 의미가 바뀐다 |

## 8. 단계

| Q | 내용 | 위험 | 종료 조건 |
|---|---|---|---|
| **Q0** | 악용 후보 6형태 등록(빨간불 없이 — 이미 차단되어야 정상) | 없음 | 전부 `일치` |
| Q1 | 조각 합산 — 파티션 (`G1`) | 낮음 | `G1` 해소, 누락차단 0 |
| Q2 | `OR` 분배 (`G5`) | 중간 | **사용자 결정 후** 착수 |
| Q3 | 겹 잇기 (`F2`·`H6`·`K4`) | **높음** | §5.3 네 조건 + 악용 6형태 유지 |

**Q0을 먼저 하는 이유**: 악용 형태들이 *지금* 차단되는지 확인하지 않으면, 완화 후 그것이 뚫려도
"원래 그랬는지 내가 뚫은 건지" 알 수 없다. 완화의 기준선이다.

## 9. 위험

1. **겹 잇기가 우회를 연다** — 지금 막혀 있는 것 중 일부가 "겹을 따로 보기 때문에" 막힌다.
   §5.3의 네 조건이 그 경계이며, 조건 하나라도 빠지면 그 자리가 구멍이다. Q3은 적대 검증 필수.
2. **`OR` 신뢰의 확산** — 파티션에 허용하면 필수 술어에도 요구가 온다. §5.2를 결정으로 못 박는다.
3. **완화가 감사를 흐린다** — "왜 통과했는가"가 안 보이면 사후 재구성이 불가능하다(I5).
4. **내가 안전하다고 단정하는 것** — 이 세션에서 다섯 번 부풀렸다. 각 완화는 형태로 증명하고,
   증명하지 못하면 완화하지 않는다.
