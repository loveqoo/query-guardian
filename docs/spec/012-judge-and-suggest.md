# 012 — 판정하고 제안한다 (서버는 사용자의 SQL을 바꾸지 않는다)

> 상태: **초안 (사용자 검토 대기)**
> 작성: 2026-07-27 · 근거: **spec 008 §0 정정**(자동 재작성은 AI 유추였다) · ADR 001

## 1. 모델

```
사용자가 쓴다 → 판정한다 → 위반이면 막고 **제안한다** → 사용자가 고친다 → **원문 그대로** 실행한다
```

서버가 사용자의 SQL을 **말없이 바꾸지 않는다.** 마스킹이 필요하면 룰로 등록해 규제하고,
고칠 방법은 제안으로 준다 — IDE가 "이렇게 고치시겠습니까"를 띄우는 것과 같다.

## 2. 무엇이 없어지고 무엇이 남는가

| | 지금 | 이후 |
|---|---|---|
| MASK 치환 | 서버가 `mask_email()`로 **바꿔 실행** | 위반으로 **막고** 마스킹 형태를 **제안** |
| FILTER 주입 | 서버가 `WHERE`에 **끼워 넣음** | 위반으로 **막고** 추가할 조건을 **제안** |
| LIMIT 주입 | SQL에 `LIMIT cap+1` 주입 | **그대로 유지** — IR을 통해 벤더별로 붙인다(§4) |
| 실행 대상 | 재작성된 SQL | **사용자가 쓴 SQL** |
| `RewriteVerifier` | 재작성 결과 재검증(실행 전제) | **제안 검증**으로 — 제안이 룰을 실제로 만족시키는지 |
| `preview-rewrite` | 저장 전 미리보기 | **제안 API의 본체** |

**엔진(706줄)은 버리지 않는다 — 출력처가 바뀐다.** 실행 변환기에서 제안 생성기로.

### 함께 사라지는 복잡도

재작성이 실행 경로에서 빠지면 **판정 대상과 실행 대상이 갈라지는 위협**(spec 008 §2.5-1)이
문제와 함께 없어진다. 그것을 막으려고 쓴 장치들이 근거를 잃는다:

- 결정 13의 **불투명 AST 핸들**(판정한 그 AST를 고친다) — 고칠 일이 없다
- `scopeId` **난스**(다른 파싱의 id가 우연히 맞는 것 방지) — 재작성 대상 지목이 없다
- `RewriteVerifier`의 **실행 전 재검증** — 실행되는 것이 원문이므로 검증할 변환이 없다

**이 절은 "지울 수 있다"가 아니라 "근거를 잃는다"까지만 말한다.** 실제 제거는 §7 단계에서
하나씩, 각각 되돌려 실패로 확인하며 한다.

## 3. ⚠️ 이 모델이 만드는 새 요구 — 마스킹 형태를 **쓸 수 있어야** 한다

지금은 사용자가 정답을 **쓸 수 없다.** 실측(2026-07-27):

```sql
SELECT mask_email(email) FROM users LIMIT 10   →  현재 BLOCK
```

재작성이 있을 때는 무해했다(서버가 알아서 했으니까). **제안 모델에서는 치명적이다** —
유일한 정답 경로가 막혀 있고, 사용자는 제안을 받아 적용해도 여전히 막힌다.

원인은 백로그 **D-A**다: `mask_email(email)`과 `CONCAT(email,'')`을 구별할 방법이 없어
**표현식으로 감싼 것을 전부 비투영으로 취급**한다.

### 목록은 이미 있다 — 만들 것은 비교뿐 (2026-07-27 사용자 논의)

허용 함수 저장소를 새로 만들지 않는다. **MASK 제약의 강제식이 곧 그 목록이다**:

```
constraint_def(kind=MASK, expression='mask_email({col})')  →  users.email 에 매핑
```

스튜어드가 이미 등록하고 있고 화면도 있다. 재작성기가 "무엇으로 바꿀지" 계산할 때 쓰던 바로 그 값을,
이제 **사용자가 쓴 것과 비교하는 데** 쓴다. 치환 코드(`Expressions.substitute`)도 그대로 재사용한다.

| 사용자가 쓴 것 | 판정 |
|---|---|
| `mask_email(email)` | 등록된 형태와 일치 → **통과** |
| `CONCAT(email, '')` | 일치하지 않음 → **막힘** |
| `email` (맨몸) | 가리지 않음 → **막힘** |

비교는 **텍스트가 아니라 구문 단위**로 한다 — 대소문자·공백·한정자(`u.email`)가 달라도 같게 봐야 한다.
IR이 이미 AST를 갖고 있으므로 새 파싱이 필요 없다.

**한 컬럼의 정답은 그 컬럼에 매핑된 def의 형태다.** `mask_email(phone)`은 `phone`의 def가
`mask_email`일 때만 유효하다 — 함수 이름만 보고 통과시키지 않는다.

**D-A는 백로그가 아니라 이 스펙의 선행 조건이다.** 다만 규모는 **판정 비교 로직 하나**다.

## 4. 행 상한 — **지금 방식을 유지한다** (2026-07-27 사용자 결정)

> "쿼리를 완전하게 수정하지 말자는 것은 아닙니다. 우리에겐 IR 레이어가 있고
> 이를 통해 각 벤더에 맞게 limit을 추가할 수 있습니다."

**바꾸지 않는 것은 값과 조건**(마스킹·필터)이다 — 결과의 **의미**를 바꾸는 것들.
**행 상한은 양을 자를 뿐**이고 사용자가 확정한 안전장치 4종에 들어 있다. IR을 통해 벤더별로
`LIMIT`을 붙이는 지금 방식이 본체이며, 이 스펙은 그것을 건드리지 않는다.

### 초안이 두 번 틀렸다 — 둘 다 측정·지적으로 뒤집혔다

| 초안의 선택 | 왜 틀렸나 |
|---|---|
| ⓓ 커넥션에 `SQL_SELECT_LIMIT` | **사용자 `LIMIT`이 이긴다**(실측: 세션 3에 `LIMIT 9` → 9행). `LIMIT 100000`을 쓰면 상한이 없다 |
| ⓐ `statement.maxRows` | MySQL에서는 서버를 멈추고 사용자 `LIMIT`도 이긴다(실측). 그러나 **JDBC 구현은 드라이버마다 다르다** — 결과를 다 받고 앞의 n개만 주는 드라이버라면 감사엔 "10행"인데 전부 건너온 것이 된다. **벤더마다 다시 재야 하는 보장은 보장이 아니다** |

멀티 벤더가 예정된 제품에서 IR 주입이 **벤더 무관하게 서버를 멈추는 유일한 방법**이다.
측정으로 얻은 사실은 버리지 않고 `QueryExecutor`의 KDoc에 남겼다 — 다음 사람이 같은 길을 또 가지 않게.

## 4-1. 결정 (2026-07-27 사용자)

| 물음 | 결정 | 뜻 |
|---|---|---|
| 마스킹 없이 **이미 저장된 쿼리** | **실행할 때 막힌다** | 일괄 변환·사전 표시 없음. 사용자가 고치는 것 자체가 새 모델이다 |
| 제안 조각을 어디에 | **차단 응답에 함께** | 요청 한 번으로 끝난다. 화면은 받은 것을 그대로 보인다 |
| 근거 잃은 장치 정리 | **이번에 이어서** | 죽은 코드를 남기면 다음 사람이 "아직 쓰이나"를 판단하느라 시간을 쓴다 |

## 5. 불변식

| # | 불변식 | 왜 |
|---|---|---|
| I1 | **의미는 바꾸지 않는다** — 값(마스킹)·조건(필터)을 서버가 고치지 않는다. **양(행 상한)만 자르고 그 사실을 보인다** | 몰래 바꾸는 것과 보이게 자르는 것은 다르다. 상한은 사용자가 확정한 안전장치이고 화면·감사에 드러난다 |
| I2 | 제안은 **적용해도 되고 안 해도 된다** — 적용하지 않으면 그냥 막힌다 | 제안이 강제가 되면 재작성으로 되돌아간다 |
| I3 | **제안은 룰을 실제로 만족시켜야 한다** | 만족시키지 못하는 제안은 사용자를 헛돌게 한다. 제안 생성 후 **그 결과를 다시 판정**해 확인한다 |
| I4 | 행 상한은 **서버가 멈추게** 한다 | 클라이언트에서 세다 마는 것은 통제가 아니라 표시다 |
| I5 | 사용자가 **정답을 쓸 수 있어야** 한다 | §3 — 제안대로 고쳐도 막히면 모델이 성립하지 않는다 |

## 6. 수용 기준

| # | 기준 | 재는 방법 |
|---|---|---|
| A1 | 실행된 SQL == 감사의 `original_sql` | 통합 테스트에서 문자열 동등 |
| A2 | `mask_email(email)`을 손으로 쓴 쿼리가 **통과**한다 | `ShapeCoverageTest`(현재 BLOCK, 고치면 해소) |
| A3 | 마스킹 안 된 조회는 **막히고**, 응답에 **제안이 실린다** | E2E |
| A4 | 제안을 적용한 SQL이 **판정을 통과**한다 (I3) | 제안 → 재판정 왕복 테스트 |
| A5 | 행 상한·`moreRowsExist` 세 상태가 **그대로 유지된다** | 기존 통합 테스트 |

| A7 | 형태 커버리지 회귀 없음 | `ShapeCoverageTest` 55형태 |

제품이 된다. 순서를 바꾸면 그 구간 동안 마스킹 대상 컬럼을 아무도 조회할 수 없다.

### 7-1. P2c — 조건 끼워넣기 제거 (2026-07-27 사용자 결정)

**P2는 마스킹만 걷었다.** `RewritePlanner.planInjections`가 남아 실행 시점에 여전히 WHERE에
조건을 붙인다 — **I1("조건을 서버가 고치지 않는다")을 어기고 있다.** 발견은 M3 착수 직전.

걷어내기 전에 **덮이지 않는 자리**가 하나 있다(실측):

| 제약 종류 | 판정이 요구하나 | 주입하나 | 걷어내면 |
|---|---|---|---|
| `FILTER` | **예** — `RequirePredicateRule` | 예 | 무해. 중복이 사라질 뿐 |
| `INTEGRITY` | **아니오 — 어느 룰도 안 본다** | 예 | **강제 수단이 사라진다 = fail-open** |

`RequirePredicateRule`은 `catalog.requiredPredicates`를 읽고 그것은 `DefKind.FILTER`만 거른다.
`INTEGRITY`는 **주입만이 유일한 강제 수단**이었다. 그대로 지우면 스튜어드가 등록한 무결성 조건이
화면엔 있는데 아무 일도 안 하게 된다.

> 사용자 결정: **"판정으로 옮긴다"** — FILTER와 똑같이, 사용자가 그 조건을 직접 안 쓰면 막고
> 무엇을 써야 하는지 제안한다.

**순서(뒤집으면 그 구간이 fail-open이다):**

1. `requiredPredicates`가 `FILTER` + `INTEGRITY`를 함께 읽게 한다 → **판정이 넓어진다(강화)**.
   `ShapeCoverageTest`에 INTEGRITY 형태를 **먼저** 추가해 빨간불을 본다(spec 011 원칙 ⑵).
2. 그 다음에 `planInjections`·`SqlRewriter`의 주입 경로를 지운다.
3. 도달 불가가 되는 것들을 확인한다 — `RewriteRefusal.OUTER_JOIN_FILTER`와 그 감사 코드.
   이것은 **손실이 아니라 회수**다: 지금 LEFT JOIN 쿼리가 "주입하면 조인 의미가 INNER로 바뀐다"는
   이유만으로 실행 단계에서 거절되는데, 주입이 없으면 거절할 이유가 없다.
4. 각 제거를 **되돌려 실패**로 확인한다. 되돌린 값이 정말 다른 뜻인지부터 본다(retrospect 020 §3-⑷).

**남는 것**: 행 상한(`LIMIT`)과 논리명→물리명 치환. 둘 다 **의미가 아니라 양·이름**이다(I1).

**미루는 것**: 소프트 삭제를 *포함해서* 보고 싶은 경우. 사용자가 이미 짚었다 —
> "소프트삭제인 경우 의도하는 것에 따라 필요할 수도 있고, 아닐 수도 있습니다.
> 룰을 설정하는 요청만 있고, 룰을 제외하는 기능은 요청서에 없군요."

이것은 **요청서가 규칙을 고른다**(별도 스펙)의 일이다. P2c는 그때까지 "항상 요구"로 둔다 —
막는 쪽이 안전한 방향이고, 필요하면 사용자가 조건을 쓰면 통과한다.

### 7-2. P4 — 되돌림 (기록)

죽은 마스킹 기계를 지우려다 되돌렸다. 그 코드를 **대상이 아니라 도구로** 쓰는 테스트가 일곱 있다
(스코프 지목·계획-AST 불일치 거절·핸들 단회 사용). 착수 순서는 `.dev/BACKLOG.md`.
**P2c가 이것을 줄인다** — 주입까지 사라지면 남는 재작성이 두 종류뿐이라, 테스트의 재료를
그쪽으로 갈아타기가 쉬워진다.

### 7-3. P5 — 제안을 구조로 준다 (2026-07-27 사용자 결정)

P3의 제안은 **위반 메시지 문장 안**에 들어 있다:

```
"컬럼 email은(는) 가려서 조회해야 합니다 — `mask_email(email)` 로 바꿔 주세요."
```

화면은 이 문장에서 정규식으로 뽑는 수밖에 없고, **어디를 고쳐야 하는지 모른다.**

> 사용자 결정: **"클릭하면 적용"** — 근거는 §0에서 사용자가 밝힌 모델이다.
> *"하지만 쿼리 추천은 해줄 수 있어야 합니다. 코드 추천해주듯이 말이죠."*

`ViolationDto`에 **선택 필드**로 조각을 싣는다(기존 `message`는 그대로 — 화면이 안 바뀌어도 깨지지 않는다):

| 필드 | 뜻 | 예 |
|---|---|---|
| `kind` | 어떤 조치인가 | `REPLACE_PROJECTION` · `ADD_PREDICATE` |
| `table`·`column` | 어디에 | `users` · `email` |
| `from`·`to` | 무엇을 무엇으로 | `email` → `mask_email(email)` |

`ADD_PREDICATE`는 `from`이 없다 — 바꾸는 게 아니라 **더하는** 것이다. 이 비대칭을 타입으로 드러낸다
(`from: String?`이 아니라 조각 종류를 갈라서). **§5 I3은 그대로다** — 제안이 룰을 실제로
만족시키는지는 P3의 왕복 테스트가 계속 재고, 조각이 늘면 조각마다 왕복한다.

**하지 않는 것**: 고쳐진 SQL 전문 생성(§9). 화면이 조각을 에디터에 적용하는 것은 화면의 일이다.

## 8. 하지 않는 것

- 판정 로직 변경 — spec 011이 별개로 진행 중이며 이 모델에서 **더 중요해진다**(판정이 유일한 통제).
- IR 교체(Calcite) — ADR 001에서 **재검토 예약**으로 결정. 이 스펙은 그것과 독립이다.
- 제안의 UI — M3(실행 UI)에서 다룬다. 이 스펙은 **서버가 무엇을 주는가**까지다.
- **고쳐진 SQL 전문 생성** — §9 참조.

## 9. 제안의 형태 — 조각으로 준다 (2026-07-27 사용자 결정)

> "쿼리 전문은 필요 없습니다. 이미 쿼리를 이해하고 작성하는 사람에겐 수다스럽습니다. 조각을 주면 됩니다."

고친 SQL을 통째로 만들어 주지 않는다. **무엇을 어디에 하라**만 준다:

```
users.email 은 mask_email(...) 로 감싸서 조회하세요
WHERE 에 consent_yn = 'Y' 를 추가하세요
```

**이 결정이 작업을 줄인다.** 계획 수립기가 이미 "무엇이 적용돼야 하는가"를 계산하고 있으므로
(`RewritePlan`의 항목들), SQL을 조립하는 단계 없이 그 항목을 문장으로 내보내면 된다.
`SqlRewriter`의 **조립·주입 부분은 제안에 필요 없다**.

각 조각은 **대상(테이블·컬럼)과 조치**를 함께 갖는다 — 화면이 해당 위치를 짚어 줄 수 있어야 하고,
그것이 §5 I3(제안이 룰을 실제로 만족시키는지)을 확인할 단위이기도 하다.
