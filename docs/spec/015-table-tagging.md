# spec 015 — 테이블 태깅: 구조가 맞으면 자동으로 덮인다

- **일자**: 2026-07-28
- **상태**: 초안 (사용자 검토 대기)
- **관련**: `.dev/learning/020` · `docs/spec/002`(제약 카탈로그) · `docs/spec/014` Phase 1

---

## 1. 왜 필요한가 — 구멍들의 뿌리가 하나였다

Phase 1에서 찾은 구멍들이 서로 달라 보이는데 뿌리가 같다.

| 구멍 | 실제 원인 |
|---|---|
| 새 목적을 만들면 제약이 0개 | 사람이 목적별로 다시 등록해야 함 |
| 새 테이블은 경고만 (`unknown-table`은 WARN) | 사람이 카탈로그에 넣어야 함 |
| 매핑을 잊으면 그 컬럼은 통제 밖 | 사람이 컬럼마다 매핑해야 함 |

전부 **"사람이 손으로 등록해야 덮인다"**이다. 이 저장소는 같은 실패를 IR에서 이미 겪고 처방까지 적었다.

> **열거의 누락은 조용하다.** 예외도 로그도 없고 검사기가 "없다"고 정직하게 답한다.
> 기본값을 뒤집어라 — "적은 것만 검사"에서 **"전부 훑고 뺄 것만 뺀다"**로.
> — `.dev/learning/020`

IR의 컬럼 수집에는 그 처방을 적용했다. **카탈로그는 아직 손으로 나열하고 있다.**
태깅은 같은 처방을 카탈로그에 적용하는 것이다.

## 2. 사용자 결정 (2026-07-28)

| 물음 | 결정 | 원문 |
|---|---|---|
| 식별 방식 | 테이블을 **덕 타입**으로 — 어떤 컬럼이 있는지로 본다 | "각 테이블을 덕타입 테이블로 보고, 조건이 밎으면 (특정 프로퍼티가 있으면) 태깅 합시다" |
| 태그의 정의 | 어떤 프로퍼티가 존재한다 | "태그는 어떤 프로퍼티가 존재한다 정도로 정의하고 모든 테이블을 주기적으로 훑습니다" |
| 규칙의 소속 | 태그에 등록하고, 태그된 테이블이 **필수로** 받는다 | "그 태깅 정보를 기반으로 기본적인 룰이 등록이 되어있고, 테이블이 태깅되면 해당 테이블은 필수로 태깅에 속한 룰이 적용됩니다" |
| 컬럼 이름의 다양성 | 후보를 **지정할 수 있어야** 한다 | "대상컬럼은 user_id도 될 수 있고, userid도 될 수 있습니다. 이걸 지정할 수 있어야 하며" |
| 규칙이 보는 것 | **실재하는 컬럼만** | "태깅에 속한 규칙은 명확하게 존재하는 컬럼으로만 작동합니다" |

## 3. 모델 — 태그는 **바인딩**이지 이름표가 아니다

```
태그 정의
  이름: 개인정보테이블
  역할 「사용자 식별자」 후보 = user_id | userid | member_id | ...

태그 적용 결과 (테이블마다)
  orders   → 개인정보테이블 { 사용자 식별자 = user_id }
  sessions → 개인정보테이블 { 사용자 식별자 = userid }

태그 규칙
  "목록 조회 시 「사용자 식별자」가 조건에 있어야 한다"
```

**규칙은 추상 이름으로 쓰고, 판정은 실재 컬럼으로 한다.** 역할을 실제 컬럼으로 푸는 것이 태그의 일이다.

### 3.1 핵심 — 태그는 **매핑 생성기**다 (새 판정 축이 아니다)

실측 확인: 판정이 제약을 얻는 경로는 **하나**다 — `ConstraintBindingReader.forTable()`.
모든 룰이 보는 `DbTableCatalog`가 그것만 읽는다.

그러므로 **태그가 만드는 것은 `ConstraintMapping`이면 된다.** 그러면:

- 판정·제안·감사 계층이 **한 줄도 안 바뀐다**
- **새 fail-open 표면이 안 생긴다** — 새 판정 경로를 만들면 기존 경로와 그 사이로 샌다
  (spec 008에서 판정과 재작성의 순회 축이 달라 평문이 4경로로 샌 실측이 있다)
- 형태 커버리지 76개를 비롯한 검증 자산이 그대로 유효하다

즉 이 스펙의 본체는 **"수동 매핑"과 "자동 매핑"을 같은 자리에 놓는 것**이고,
판정은 그 둘을 구별하지 않는다.

## 4. 불변식

- **I1. 규칙은 실재하는 컬럼만 본다.** 역할이 그 테이블에서 어떤 컬럼으로도 안 풀리면
  그 규칙은 **그 테이블에 적용되지 않는다** — 없는 컬럼에 조건을 요구하면 모든 쿼리가 막힌다.
  단, 그 사실은 조용히 넘어가지 않는다(I4).
- **I2. 태그가 만든 매핑은 사람이 만든 매핑과 구별된다.** 재스캔이 사람 손을 덮어쓰면 안 되고,
  "이 제약이 왜 걸려 있나"에 답할 수 있어야 한다. → `ConstraintMapping`에 출처 필드 추가.
- **I3. 붙는 것은 자동, 떨어지는 것은 자동이 아니다.** 스키마가 바뀌어 태그 조건이 안 맞게 되면
  **규칙이 조용히 사라진다.** 통제가 없어지는 변화는 사람이 확인해야 한다.
- **I4. "못 붙였다"는 결과가 아니라 사건이다.** 후보가 여럿이라 모호하거나, 하나도 안 맞거나,
  구조가 의심스러운데 태그가 안 붙은 테이블은 **목록으로 남는다.** 조용한 미적용이 가장 나쁘다.
- **I5. 태그 어휘도 통제 대상이다.** 규칙이 참조하는 역할 이름은 등록된 것만 쓸 수 있다
  (spec 002의 2계층 통제를 태그에도 적용 — 자유 문자열이면 오타가 규칙에 들어간다).

## 5. 사람이 정해야 하는 것 — AI가 정하지 않는다

### D1. 후보가 여럿 맞을 때

테이블에 `user_id`와 `userid`가 **둘 다** 있으면 역할이 어느 쪽인가?

- **(가) 모호하면 태그를 안 붙이고 사람에게 넘긴다** — fail-closed. 대신 그 테이블은 그동안 통제 밖이다.
- **(나) 후보 목록의 순서를 우선순위로 쓴다** — 자동으로 정해지지만 **틀린 컬럼을 골랐을 때 조용하다.**

> 이 저장소의 기본 성향은 (가)다 — "모른다"와 "없다"를 같은 값으로 쓰지 않는다.
> 다만 (가)는 **미적용 구간**을 만들므로 I4의 목록이 실제로 읽혀야 의미가 있다.

### D2. 하나도 안 맞을 때

`owner_ref`처럼 후보에 없는 이름을 쓰는 테이블. 그냥 넘기면 **덕 타이핑이 못 잡는 10%가
정확히 위험한 10%**가 된다(특이한 이름일수록 특이한 테이블이다).

- 사람이 **직접 바인딩**할 길이 필요하다(역할 → 컬럼 수동 지정).
- 그리고 "PII 같은 컬럼은 있는데 식별자를 못 찾은 테이블"은 I4 목록에 올라야 한다.

### D3. 집계 면제의 경계 — **여기가 가장 위험하다**

사용자 예시: *"개인정보 테이블은 **목록 조회(카운트 아님)** 시 user_id가 반드시 조건에 들어가야 한다."*

문제: **카운트도 오라클이다.**

```sql
SELECT COUNT(*) FROM users WHERE ssn = '900101-1234567'
```

결과가 0이냐 1이냐로 **그 주민번호의 존재 여부**를 알아낸다. 행을 한 줄도 안 받고 개인을 특정하고,
값을 바꿔가며 반복하면 데이터를 복원한다. 즉 **"카운트는 안전하다"는 참이 아니다.**

선택지:

- **(가) 집계 면제 없음** — 개인정보 테이블은 카운트도 식별자 조건을 요구한다. 가장 안전하고 가장 불편하다.
- **(나) 집계 면제하되 조건을 제한** — 예: 조건에 등호 비교가 있으면 면제 안 함(개인 특정 가능).
  경계를 어디에 그을지가 설계 문제이고, **잘못 그으면 오라클이 열린다.**
- **(다) 집계 면제 + 결과 하한** — 카운트가 K 미만이면 거절(k-익명성의 가장 단순한 형태).
  실행 후 판단이라 **감사·차단 시점이 지금 모델과 다르다.**

### D4. 훑기 주기와 그 사이 구간

주기적으로 훑으면 **스키마가 바뀌고 태그가 갱신되기 전까지**가 열린다.
새 테이블이 생겼는데 아직 안 훑었으면 지금은 `unknown-table`(WARN)이라 통과한다.

- 훑기를 언제 도는가 (기동 시 / 주기 / 카탈로그 변경 시)
- 그 사이 구간에서 **모르는 테이블을 어떻게 볼 것인가** — WARN 유지인가 BLOCK인가

## 6. 선행 작업

- **IR에 집계 축 추가** (D3이 (가)가 아니면 필수).
  현재 `SelectItem.Expr(text)`는 **텍스트 덩어리**다 — `COUNT(*)`도 `mask_email(email)`도 `SUM(x)`도
  전부 `Expr`이라 구조로 구분되지 않는다. 문자열에서 `COUNT(`를 찾는 방식은 이 저장소가 금지한다
  (공백·대소문자·주석으로 뚫린다 — spec 001 §6.5).
- **`ConstraintMapping`에 출처 필드** (I2).
- **역할 어휘 등록 경로** (I5).

## 7. 완료 조건 (관측 가능한 것만)

- 태그 정의 하나와 후보 컬럼 목록을 등록하면, **이름이 다른 두 테이블**이 각자 자기 컬럼으로 바인딩된다.
- 태그가 만든 매핑으로 **기존 룰이 그대로 발화한다** — 판정 코드 변경 0줄로.
- 재스캔이 **사람이 만든 매핑을 덮어쓰지 않는다**(되돌려 실패로 확인).
- 태그 조건이 안 맞게 되면 **경고가 나고 규칙이 자동으로 사라지지 않는다**(I3).
- I4 목록이 비어 있지 않은 상태를 만들 수 있다 — 모호·미매칭 테이블이 실제로 거기 뜬다.
- 형태 커버리지·우회 스위트가 **그대로 초록**이다(판정 축이 안 늘었다는 증거).

## 8. 비목표

- **컬럼 값을 보고 판단하지 않는다.** 태그는 **구조**(어떤 컬럼이 있는가)만 본다.
  값을 보려면 데이터를 읽어야 하고, 그것은 이 제품이 통제하려는 바로 그 행위다.
- **태그가 수동 카탈로그를 대체하지 않는다.** 병행이다 — 자동은 흔한 경우를 덮고,
  특이한 경우는 사람이 짚는다. 대체로 가면 D2의 10%가 통째로 빈다.
